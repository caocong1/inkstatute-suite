# Production Memory System Strategy

**Date:** 2026-07-02
**Milestone:** v1.3 Production Memory System and Evaluation Spikes
**Status:** Proposed implementation contract

## Decision

InkStatute should build a production-grade platform-native memory system first, then evaluate external memory systems through sanitized adapters. External systems such as Zep, Hindsight, OpenViking, ReMe, and Mem0 remain candidates for future adoption, but none should become the live legal memory default until they beat the native path on privacy, deletion/export, tenant isolation, traceability, relevance, latency, operations, and procurement gates.

This is a legal-product decision, not a generic AI-memory ranking. The memory layer must help the lawyer assistant remember useful context while keeping contract logs and source references authoritative, preserving human review for high-risk legal conclusions, and avoiding raw customer/legal payload storage by default.

## Why Native First

The v1.2 foundation already provides the right platform seams:

- `MemoryRecord`, `MemoryCandidate`, `MemoryUse`, `ContextBundle`, and `RunInterrupt` contracts.
- `InMemoryMemoryStore`, `FeedbackLearningPolicy`, and `ContextAssembler` as dependency-free runtime surfaces.
- WeCom session runtime and ingress wiring that can attach refs-only context metadata to backend-bound runs.
- `MemoryStoreAdapter` and `MemoryStoreCapabilityManifest` for future external providers.

The missing work is not "pick a memory SaaS." The missing work is the production loop:

1. Durable reference-first memory storage.
2. Automatic rolling summary creation without embedding raw legal text in context metadata.
3. Scoped recall before backend submission.
4. Feedback-to-memory candidates with human approval.
5. Deletion/export/tombstone workflows.
6. Evaluation evidence proving the above under sanitized legal-like scenarios.

Building this natively gives InkStatute full control over legal privacy, review policy, deletion semantics, and audit evidence. External tools can still be adopted later behind the same adapter boundary if their measured value justifies the operational and compliance cost.

## Borrowed Design Lessons

| Source family | Keep | Do not copy blindly |
|---|---|---|
| Zep-style graph memory | Treat cross-thread relationships and right-to-be-forgotten behavior as first-class evaluation dimensions. | Do not make hosted graph storage the default before residency, deletion, procurement, and graph-deletion semantics pass legal review. |
| Hindsight-style audit memory | Separate retain, recall, and reflect behavior; require audit logs for mutating memory operations. | Do not send live legal text to a memory engine until provider/model data flow is approved. |
| OpenViking/ReMe-style file memory | Preserve human-readable exports, inspectable memory evidence, and source-chain review. | Do not adopt file trees without tenant permissions, locking/concurrency, encryption, and deletion/export procedures. |
| Mem0-style memory layer | Keep the API ergonomics: add/search/update/delete/export, scoped filters, and fast PoC paths. | Do not store extracted legal facts automatically without policy, human review, and audit evidence. |
| Letta/MemFS-style separation | Distinguish pinned/current context from archival memory queried on demand. | Do not move agent-self-editing memory into legal production without review and rollback controls. |

## Target Architecture

### 1. Durable Native Memory Store

Add a persistent implementation behind the existing runtime memory contracts. The first production-capable target should be dependency-light and locally operable, preferably SQLite for embedded development with a Postgres-compatible shape for hosted deployment.

The store should persist only:

- IDs, scopes, statuses, timestamps, TTL/expiry, tombstones, deletion reasons.
- `source_refs`, `raw_payload_ref`, `summary_ref`, `artifact_refs`, and other safe refs.
- Hashes, lengths, confidence, labels, sensitivity, review state, and policy metadata.
- Optional short summaries only when generated by an approved summarizer policy and safe for storage.

It must reject raw payload keys, full document text fields, customer document text, secrets, complete identity numbers, and unreviewed high-risk legal conclusions.

### 2. Rolling Summary Pipeline

The current runtime can carry `summary_ref`, but it does not generate summaries. v1.3 should add a summary producer that consumes safe source references, writes summary content to an approved reference store, and updates `RollingSummaryRecord` with refs, hash, length, task intent refs, constraint refs, open question refs, artifact refs, and outcome refs.

The summary pipeline should be policy-driven:

- Trigger on turn count, token estimate, task completion, or explicit host request.
- Fail closed when source refs are missing or unsafe.
- Keep raw source content outside `ContextBundle` metadata.
- Record enough evidence to replay why a summary was created or updated.

### 3. Memory Recall Orchestrator

Add a pre-run orchestration layer between WeCom ingress/session resolution and backend submission:

1. Resolve session and scope.
2. Query approved memory records by tenant/workspace/user/session, labels, source refs, TTL, sensitivity, and relevance.
3. Select bounded `memory_refs`.
4. Load current rolling summary ref.
5. Pass `recent_turn_refs`, `memory_refs`, `summary_ref`, feedback correction refs, and output-policy refs to `ContextAssembler`.
6. Submit backend-bound `RunRequest` with a serialized `context_bundle`.

The orchestrator must not retrieve memory across tenant/workspace/user/session boundaries unless an explicit wider scope is approved by policy.

### 4. Feedback-to-Memory Review Loop

Feedback should influence the next context immediately as correction refs where safe. Durable memory writes require review:

- Positive/negative/correction feedback creates evidence.
- Repeated negative feedback can create `MemoryCandidate`.
- Route mismatch and skill candidates remain human-reviewed with `no_auto_modify`.
- A reviewer can approve, reject, tombstone, or edit a candidate.
- Approved candidates become `MemoryRecord` entries with source refs and review metadata.

This keeps learning useful without letting legal conclusions mutate themselves.

### 5. Evaluation Harness

Before adopting any external provider, InkStatute needs a repeatable memory evaluation suite:

- Multi-turn sanitized legal-like scenarios.
- Cross-session recall scenarios.
- Tenant/user/session isolation tests.
- Deletion/export/tombstone tests.
- Feedback correction and repeated-negative candidate tests.
- Long-context budget and token-impact tests.
- Source traceability and false-recall checks.
- P50/P95 latency, relevance, and context-size metrics.

The native store becomes the baseline. External candidates must run the same tests through `MemoryStoreAdapter` and produce comparable evidence.

## External Provider Spike Policy

External spikes may run only under these conditions:

- Synthetic or sanitized fixtures only.
- No live legal/customer payloads.
- No committed credentials, tokens, API keys, databases, logs, or provider output containing sensitive text.
- Provider calls are isolated behind `MemoryStoreAdapter`.
- Manifest evaluation must not mark the provider `accepted_for_current_legal_use` unless every live legal memory gate is represented and approved.

Suggested spike order:

1. Zep or Hindsight for enterprise graph/audit retrieval.
2. OpenViking or ReMe for local file-auditable memory.
3. Mem0 for fast PoC ergonomics.

## Adoption Rule

An external provider can replace or supplement platform-native memory only when:

1. It passes the same fixture suite as the native store.
2. It provides deletion/export and tenant-isolation evidence.
3. It keeps raw legal/customer text out of reusable memory by default or proves an approved safe storage model.
4. It exposes source traceability and audit logs good enough for legal review.
5. It has an operator runbook for backup, restore, deletion, incident response, and rollback.
6. It beats the native path on at least one strategic dimension: cross-thread graph reasoning, audit recall quality, file-auditable evidence chain, or implementation speed without weakening safety.

## Non-Goals

- Do not make any external memory system mandatory in v1.3.
- Do not introduce a new user-facing memory UI unless the roadmap explicitly adds it later.
- Do not store full raw legal/customer text in memory records or context bundle metadata.
- Do not auto-promote high-risk legal conclusions, route changes, or skill changes.
- Do not rebuild Hermes core, router, session storage, skill registry, MCP registry, or model gateway.
