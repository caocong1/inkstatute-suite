# 案件录入（编排入口）

## 目的

每个新案件都经过相同的录入流程，以便组合保持可比性。本入口编排五个子技能的顺序调用，并维护跨子技能的入口级护栏，确保录入质量基准不被绕过。

`_log.yaml` 中的统一行让状态技能可以汇总。`matter.md` 中的叙事捕获行无法容纳的内容。`history.md` 在录入时播种为第零条目。

---

## 入口级护栏（进入任何子技能前执行）

在启动任何子技能之前，本编排入口强制执行以下四项护栏：

### 护栏 1：加载实践配置文件

读取 `litigation-legal/CLAUDE.md`（路径：`~/.claude/plugins/config/ai-for-china-legal/litigation-legal/CLAUDE.md`）。

检查关键字段是否已填充（不含 `[PLACEHOLDER]`）：
- `## 风险校准` — 用于步骤 2 风险分级
- `## 谁在使用` → 角色倾向 — 用于步骤 2 角色确认
- `## 利益冲突清除` — 用于步骤 1 冲突门槛

**配置文件缺失或含大量 `[PLACEHOLDER]` 时（临时模式）：**

> 我注意到你还没有配置你的诉讼实践档案。
>
> **两个选择：**
> - 运行 ``litigation-cold-start-interview` 技能` 配置你的档案（约 5 分钟）
> - 说「**临时模式**」，我会使用通用默认值，并在每个输出上标记 `[临时模式 — 配置你的档案以获得定制输出]`

临时模式默认值见 `../_shared/practice-profile-schema.md` → 三、技能读取契约 → 3.2 临时模式默认值。

### 护栏 2：事项工作区上下文

确认事项工作区已启用（`litigation-legal/CLAUDE.md` → `## 事项工作区` → 启用：✓）。

事项工作区默认启用：每个案件有独立的 `matters/[slug]/matter.md` 和 `matters/[slug]/history.md`。如事项工作区未启用，提示律师在配置文件中启用后再录入。

### 护栏 3：利益冲突硬门槛

**在创建任何案件文件之前，必须完成步骤 1（subject-conflict-precheck）的利益冲突检查，且状态须为「已清除 / 待处理 / 豁免」之一。**

利益冲突状态为「未执行」时，本编排入口**强制停止**——不进入步骤 2 及后续步骤，不创建任何文件（matter.md / history.md / _log.yaml 条目），直到律师通过三路径之一处理冲突状态。

详细逻辑见：`本文档「子技能：subject-conflict-precheck」章节`

### 护栏 4：目的地与特权检查

询问输出目的地（如首次询问未配置）：

- **律师角色** → 工作产物标题：「律师工作产物 — 受律师-当事人特权保护 / 保密」
- **非律师角色** → 工作产物标题：「研究笔记 — 非法律建议，供律师审查」

面向对方/外部的目的地（如发送给案件对方）会使特权保护失效。提示律师在共享前去除特权标题和内部风险评估内容。

## 硬性护栏（不可绕过）

### 动态 Intake 与输出确认

遵循 `shared/legal-document-intake/SKILL.md`：格式、保存位置和立场已由请求、文件或实践配置明确时直接执行，不重复询问；有不会覆盖原件的安全默认值时采用默认并简短说明；只有影响成果的必须项未解决，或写入目标不明、可能覆盖原件、涉及外部发送时，才输出 `[CLARIFY:]` 并暂停。永远不覆盖原件，除非用户明确指定覆盖。

### 先检索、后结论

在给出任何法律结论、条款建议或风险判断之前：

1. 优先使用可用的检索工具核对**现行有效**的法律法规、司法解释及指导性案例（注意修订、修正与废止情况）；
2. 无检索工具或无法核实时，必须在结论处明确标注「未经检索核实，请以现行有效文本为准」；
3. 禁止凭记忆断言法条编号、发文文号或生效日期。

# 主体资格预检与利益冲突门槛

> 引用规范：`../_shared/legal-basis-conventions.md`
> 本子技能可被 `litigation-legal/skills/matter-intake/SKILL.md` 编排入口调用，
> 也可通过 `「子技能：subject-conflict-precheck」章节（见本文档）` 单独触发。

## 目的

在录入任何新案件之前，从两个维度把守硬门槛：

1. **主体资格预检**：识别案件涉及的主体类型是否存在资格限制或程序瑕疵，避免案由识别错误、立案被驳或诉讼请求无法支持。
2. **利益冲突检查**：确保本律所/团队在本案中不存在利益冲突，或确认冲突状态已明确处理并记录在案。

**未完成本子技能检查之前，禁止创建任何案件文件（matter.md、history.md、_log.yaml 条目）。**

## 步骤一：主体资格预检

### 1.1 识别涉案主体类型

收集以下信息：
- **我方当事人**：律所/公司名称、实体类型（有限责任公司/股份公司/律师事务所/政府机关/自然人等）
- **对方当事人**：名称、实体类型
- **其他相关主体**：担保人、保证人、第三方等

### 1.2 特殊主体资格触发检查

对照 `shared/references/subject-qualification-traps.md`，如果案件涉及以下任一主体类型，**必须先核查主体资格**：

| 主体类型 | 核查重点 | 案由影响 |
|---------|---------|---------|
| 融资担保公司/担保公司/地方金融组织 | 是否有权出具独立保函（一般无权） | 独立保函纠纷 → 应为保证合同纠纷 |
| 银行分支机构（无总行授权） | 是否有对外担保权限 | 担保可能无效，需核验授权文件 |
| 保险公司（保证保险）| 性质争议：保险责任 vs 保证责任 | 案由不同：保险纠纷 vs 担保纠纷 |
| 上市公司（担保方）| 是否有董事会/股东会决议 | 无决议 → 担保可能无效 |
| 国企/事业单位（担保方）| 是否有国资委审批 | 程序瑕疵，担保效力待定 |
| 地方政府/政府融资平台 | 担保是否合法（预算法限制）| 担保可能无效 |
| 无行为能力人/限制行为能力人 | 是否有法定代理人 | 合同效力问题，代理权需核验 |

### 1.3 主体资格问题处理规则

- **无主体资格问题**：记录「主体资格预检：无异常」，继续执行。
- **发现主体资格问题**：
  1. 在初步记录中**显著标记**（用 `[主体资格异常 — 需复核]` 标签）
  2. 说明具体问题和对案由/请求权基础的影响
  3. 告知律师须在继续录入前确认调整后的案由
  4. 在后续 `matter.md` 的「待决问题」中保留标记，直到律师确认

## 步骤二：利益冲突检查

### 2.1 依据实践配置文件读取冲突清除策略

从 `litigation-legal/CLAUDE.md` → `## 利益冲突清除` 读取：
- **清除方法**：律所系统 / 人工检查 / 外部律师 / 其他
- **清除负责人**：姓名/团队/律所
- **并行录入政策**：配置文件是否声明「待处理状态下可并行录入」

### 2.2 收集冲突检查信息

请律师提供冲突检查的结果和元数据：

| 字段 | 说明 |
|------|------|
| **检查状态** | 已清除 / 待处理 / 未执行 / 豁免 |
| **检查对象** | 已检查的实体名称（至少包括：对方当事人、已知关联公司、对方代理律师（如已知）、关键证人）|
| **清除方法** | 与配置文件声明的方法一致 |
| **清除人** | 执行检查的人员姓名/团队 |
| **清除日期** | YYYY-MM-DD |

### 2.3 按状态的三路径门槛

**状态：已清除** → 记录元数据，继续。

**状态：待处理** → 在 `matter.md` 和 `_log.yaml` 日志行中**显著标记**冲突未决；仅在实践配置文件声明「并行录入可接受」时允许继续录入；在每次 `/matter-update` 和 `/portfolio-status` 中持续标记，直到解决。

**状态：豁免** → 需要书面豁免文件（记录豁免的存在、签署人、存放位置）。

**状态：未执行** → **停止。这是硬门槛。** 本技能不会创建 matter.md、history.md 或 _log.yaml 条目，直到冲突状态得到解决。三条可接受的路径：

#### 路径 1 — 立即运行冲突检查

暂停本次录入。按照实践配置文件中的利益冲突清除方法进行清除。带着 `状态: 已清除` 或 `状态: 豁免` 返回。

#### 路径 2 — 标记待处理并指定负责人和截止日期

仅在实践配置文件声明并行录入可接受时允许。须捕获：谁在运行冲突检查、预计何时返回、检查的具体实体。录入继续；案件行携带 `conflicts.status: 待处理`；`/portfolio-status` 每次运行都标记；`/matter-update` 重新提示直到解决。

#### 路径 3 — 跳过并记录理由

仅在用户**明确确认跳过**时允许。记录在 `conflicts.override` 中：

```yaml
conflicts:
  status: 未执行
  override:
    by: [用户姓名]
    date: [YYYY-MM-DD]
    rationale: [为什么跳过冲突检查 — 永久记录；不会自动过期]
```

此字段在每次 `/portfolio-status`、每次 `/matter` 简报和每次 `/matter-update` 中**永远可见**，直到被用户通过显式编辑 `_log.yaml` 移除。

> **不要默默进行。** 「我稍后做」不是可接受的回答。必须选择路径 1/2/3 之一，且选择被记录在案。

### 2.4 冲突检查的边界

本子技能**不运行冲突检查本身**——实际清除发生在实践配置文件声明的系统或判断中。本子技能的职责是：

- 记录冲突检查已执行的事实（状态/方法/检查对象/清除人/日期）
- 若未执行：按三路径门槛阻止录入
- 若存在冲突标记：确保它在所有后续工作产物中保持可见

## 步骤一：案件识别

### 1.1 基础案件信息

收集以下字段（带 * 为必填，其余可补充）：

| 字段 | 说明 | 要求 |
|------|------|------|
| **案件名称*** | 律师通常引用的案件名称（如「甲公司诉我公司合同纠纷 2026」）| 应能唯一标识案件 |
| **对方当事人*** | 主要对方当事人全称；多方并列时逐一列出 | 包含关联公司 |
| **案件类型*** | 见下方分类 | 从列表选择或组合 |
| **我方角色*** | 见角色确认规则 | 不得默默假设 |
| **管辖机构*** | 见管辖判断流程 | 须区分法院/仲裁 |

**案件类型分类：**

```
合同纠纷 | 劳动争议 | 知识产权 | 侵权 | 公司治理 | 房地产 | 建设工程 |
股权/并购 | 金融/证券 | 破产/重整 | 刑事（刑附民）| 行政 | 仲裁 | 其他
```

### 1.2 我方角色确认（绝不默默假设）

按以下规则从 `litigation-legal/CLAUDE.md` → `## 谁在使用` → `角色倾向` 确认：

| 配置文件角色倾向 | 处理规则 |
|--------------|---------|
| `原告` | 预填角色为「原告/申请人」，向律师确认本案是否一致 |
| `被告` | 预填角色为「被告/被申请人」，向律师确认本案是否一致 |
| `两者 — 默认 X` | 按默认方 X 预填，询问律师本案是否与默认一致 |
| `因案而异` 或 `[PLACEHOLDER]` | 直接询问律师，不预填 |

**角色驱动下游技能的方向：**
- **原告/申请人立场**：风险分级导向案件价值、胜诉概率、代理经济（费用/胜算）
- **被告/被申请人立场**：风险分级导向敞口/准备金/保险理赔/和解阈值

### 1.3 管辖判断流程

按以下链条逐步确认管辖：

```
第一步：是否有有效仲裁协议？
  → 有效仲裁协议 → 仲裁管辖，排除法院管辖（「或裁或审」原则）
  → 无仲裁协议 → 进入法院管辖判断

第二步：确定级别管辖（法院）
  → 参考 civil-procedure-citations.md A.2 级别管辖
  → 注意：具体标的额划分以当地高院级别管辖规定为准

第三步：确定地域管辖
  → 合同纠纷：被告住所地 or 合同履行地 [条号待验证]
  → 侵权纠纷：侵权行为地 or 被告住所地 [条号待验证]
  → 检查是否有协议管辖（须书面约定，且在法定范围内）

第四步：检查专属管辖
  → 不动产 → 不动产所在地（不可协议变更）[条号待验证]
  → 港口作业 → 港口所在地 [条号待验证]

第五步：检查专门法院管辖
  → 海事纠纷 → 海事法院
  → 重大知识产权 → 知识产权法院
  → 特定金融纠纷（上海）→ 金融法院
  → 互联网相关纠纷 → 互联网法院
```

**管辖识别结果格式：**

```
管辖类型：[法院 / 仲裁]
  如为法院：[级别] — [具体法院名称/城市]
  如为仲裁：[仲裁机构名称]（CIETAC / BAC / SHIAC / SCIA / 其他）
管辖依据：[说明为何如此判断，有仲裁协议须说明内容]
异常标记：[管辖 flagged — 需验证管辖权] / 无异常
```

### 1.4 案件来源

```
起诉状送达 | 仲裁申请送达 | 律师函 | 监管调查通知 |
内部举报 | 诉前威胁 | 其他
```

**种子文档机会：** 「如果你有 initiating 文档（起诉状、仲裁申请、律师函），附上或分享路径，能让录入更精确。」

## 步骤二：风险分级

### 2.1 对照实践配置文件校准

从 `litigation-legal/CLAUDE.md` → `## 风险校准` 读取：
- **严重程度定义**：各级别（极高/高/中/低）对应的金额阈值和业务影响描述
- **可能性定义**：各级别（高/中/低）对应的概率区间

> **重要纪律**：如果实践配置文件的风险校准字段为 `[PLACEHOLDER]`（未配置），**不得假装精确**。使用用户直觉评级，并注明「风险校准未配置，评级为用户估计值」。

### 2.2 风险分级维度

| 维度 | 选项 | 判断依据 |
|------|------|---------|
| **严重程度** | 极高 / 高 / 中 / 低 | 对照配置文件严重程度定义，考虑：金融敞口金额、业务连续性影响、声誉风险、刑事责任可能性 |
| **可能性** | 高（>70%）/ 中（30%-70%）/ 低（<30%）| 对照配置文件可能性定义，考虑：证据情况、法律依据清晰度、司法实践倾向 |
| **综合风险评级** | 极高 / 高 / 中 / 低 | 按矩阵计算（见下）|

**风险综合评级矩阵：**

| 严重程度↓ \ 可能性→ | 高 | 中 | 低 |
|--------------------|----|----|-----|
| **极高** | 极高 | 极高 | 高 |
| **高** | 极高 | 高 | 中 |
| **中** | 高 | 中 | 低 |
| **低** | 中 | 低 | 低 |

### 2.3 敞口量化

| 字段 | 说明 |
|------|------|
| **金钱敞口范围** | 最佳估计范围（如 ¥200万–¥500万）；含利息/罚款/费用 |
| **非金钱敞口** | 禁令风险 / 同意令 / 经营许可吊销 / 声誉/媒体 / 先例影响 / 刑事风险 |

## 步骤三：重大性评估

对照 `litigation-legal/CLAUDE.md` → `## 风险校准` → `### 重大性阈值`：

| 重大性级别 | 触发条件 | 后续行动 |
|---------|---------|---------|
| **已计提准备金** | 敞口下限 ≥ 准备金阈值 | 通知财务，确认准备金金额 |
| **已披露** | 敞口下限 ≥ 披露阈值 | 确认披露备案和脚注位置 |

| **无** | 低于监控阈值 | 正常录入 |

## 目的

记录案件的关键程序性期限，并对诉讼时效作出初步判断（非深度时效分析）：

1. **关键日期记录**：答辩期限、举证期限、下次听证/庭审日期、监管期限，确保律师不遗漏紧迫截止日
2. **诉讼时效起算初判**：识别案由对应的时效期间（一般3年=《民法典》第188条），初步判断起算点，标记是否临近届满
3. **深度分析路径提示**：时效中止/中断事由分析属于深度任务，本技能仅作初判并提示运行 03-03 的 `limitation-monitoring` 子技能

**本子技能不作出时效结论**——起算点不清时一律标记 `[需律师确认]` 并列出待查事实。

## 步骤一：关键程序性日期

### 1.1 答辩期限

**已核实规则**：普通程序下，被告应于收到起诉状副本之日起**十五日**内提出答辩状；举证期限不得少于**十五日**。（《民事诉讼法》2023修正，具体条号待验证）

收集以下信息：

| 字段 | 说明 | 示例 |
|------|------|------|
| **起诉状/仲裁申请送达日期** | 我方收到的日期 | 2026-04-20 |
| **答辩期限届满日** | 送达日 + 15 日（普通程序）/ 30 日（仲裁，具体规则见各仲裁机构规则 `[待验证]`）| 2026-05-05 |
| **距今天数** | 自动计算 | 如：还有 7 日 |
| **是否已提交答辩状** | 是 / 否 / 不适用 | — |

**紧急提示条件**：距答辩期限届满 ≤ 5 个工作日时，标记 `[紧急 — 答辩期限临近]`。

### 1.2 举证期限

| 字段 | 说明 |
|------|------|
| **法院/仲裁指定的举证期限** | 从开庭通知书或庭前会议确认 |
| **举证截止日期** | 具体日期 YYYY-MM-DD |
| **证据提交状态** | 已全部提交 / 部分提交 / 尚未提交 |

> **重要**：逾期举证的后果为法院一般不予认可（《证据规定》2020修正，条号待验证）。逾期须能说明正当理由。

### 1.3 下次听证/庭审

| 字段 | 说明 |
|------|------|
| **下次听证/庭审日期** | YYYY-MM-DD HH:MM（如已排期）|
| **庭审形式** | 开庭审理 / 书面审理 / 视频庭审 |
| **庭审地点** | 法院/仲裁机构名称 + 地址 |

### 1.4 监管期限（如有）

如案件涉及监管调查通知或行政程序，记录：

| 字段 | 说明 |
|------|------|
| **监管机构** | 名称 |
| **期限类型** | 答复期限 / 材料提交期限 / 其他 |
| **期限届满日期** | YYYY-MM-DD |

### 1.5 诉讼时效截止（初判，见步骤二）

在步骤二完成后填写。

## 步骤二：诉讼时效起算初判

> **纪律**：本步骤作初步判断，不下最终结论。起算点不清时不推断结论，一律标 `[需律师确认]` 并列出待查事实。深度时效分析（中止/中断事由、特殊时效、最长期间）提示运行 `limitation-monitoring` 子技能。

### 2.1 识别案由对应的时效期间

**已核实锚点：一般诉讼时效期间 = 3 年（《民法典》第188条）**

| 时效类型 | 规则 | 来源 | 状态 |
|---------|------|------|------|
| **一般诉讼时效：3 年** | 向人民法院请求保护民事权利的诉讼时效期间为三年 | 《民法典》（2020年）第188条 | **已核实** |
| 特殊时效（如票据纠纷、国际货物买卖等）| 依各专门法律确定，通常为 1 年或 4 年 `[待验证]` | 各专门法律 `[模型知识 — 需验证]` | `[待验证]` |
| **最长权利保护期间：20 年** | 自权利受到损害之日起超过二十年的，法院不予保护 | 《民法典》（2020年）第188条第2款 `[待验证]` | `[待验证]` |

**判断本案适用的时效期间：**

- 一般合同纠纷/侵权/劳动（超出劳动仲裁部分）→ 一般 3 年时效
- 票据纠纷、海事纠纷、国际货物买卖等 → 核查专门法律 `[待验证]`，标记特殊时效
- 如不确定本案案由适用的时效期间 → 标记 `[时效期间待确认 — 需律师核查]`

### 2.2 初判时效起算点

**已核实规则**：时效期间自权利人**知道或者应当知道**权利受到损害以及义务人之日起计算（《民法典》第188条）。

收集以下信息，尝试初判起算点：

| 信息项 | 说明 |
|-------|------|
| **权利受损的事件** | 违约发生日、侵权行为日、债务到期日等 |
| **我方知悉日期** | 何时知道或应当知道权利受损及义务人 |
| **合同履行期限** | 债务约定的履行期限届满日（如有）|
| **最后催告日期** | 如有书面催告，最后一次催告日期 |

**初判起算点规则：**

| 情形 | 初判起算点 |
|------|-----------|
| 有明确违约日期 | 知悉违约之日（通常为违约日当日或合理知悉后）|
| 债务有明确到期日 | 到期日起 |
| 分期履行债务 | 最后一期履行期届满之日 `[待验证]` |
| 未约定履行期限的债务 | 催告后合理期限届满之日 `[待验证]` |
| 连续侵权 | 侵权行为终止之日（争议，标 `[需律师确认]`）|

> **不确定时**：不推断，直接标记 `[起算点不确定 — 需律师确认]` 并列出待查清的关键事实。

### 2.3 计算初步时效届满日

```
初步时效届满日 = 起算日 + 3 年（或对应特殊时效期间）
```

| 时效状态 | 标记 |
|---------|------|
| 距届满 > 1 年 | 常规监控 |
| 距届满 6 个月 ~ 1 年 | `[时效预警 — 距届满不足1年，建议启动时效监控]` |
| 距届满 < 6 个月 | `[时效紧急 — 距届满不足6个月，需立即评估起诉/仲裁必要性]` |
| 已届满（疑似）| `[时效疑似届满 — 需律师立即核查时效中止/中断事由]` |
| 起算点不清 | `[时效起算点不确定 — 需律师确认后方可计算]` |

### 2.4 时效中止/中断事由（初步标记）

本技能**不分析**时效中止/中断事由——该工作属于深度时效分析任务。初判阶段仅询问：

- 是否有书面催告（如有，记录最近一次日期）？
- 是否有起诉或申请仲裁的记录（如有，记录日期）？
- 是否有义务人书面承认债务的文件？

以上任一情形存在，标记 `[可能存在时效中断事由 — 建议运行 limitation-monitoring 深度分析]`。

## 步骤三：深度分析路径提示

如果存在以下任一情形，向律师提示运行深度时效分析：

- 时效距届满 < 1 年
- 案件涉及多个权利，各权利起算点可能不同
- 有疑似时效中止/中断事由
- 适用的时效期间本身不确定（特殊时效）
- 最长权利保护期间（20 年）可能已过

**提示内容：**

> 本次录入完成后，建议运行 ``litigation-limitation-monitoring` 技能` 进行深度时效分析，包含：时效期间识别 / 起算点精确判定 / 中止中断事由完整分析 / 监控台账与预警机制建立。

## 边界条件

| 情形 | 处理方式 |
|------|---------|
| 起算点有争议（对方可能主张不同起算点）| 列出双方可能的起算点，不下单方面结论，标记 `[起算点争议 — 需律师评估]` |
| 案件涉及多个独立权利（如多笔货款）| 逐笔计算时效，不合并处理 |
| 仲裁程序时效规则与诉讼不同 | 仲裁案件时效同样适用民法典，但仲裁申请中断时效规则与起诉相同 `[待验证]` |
| 当事人口述时效期间与民法典不符 | 触发法律事实合理性检查（见 practice-profile-schema.md 规则 2），标记 `[前提 flagged — 需验证]` |
| 案件处于诉前阶段，无送达日期 | 记录「尚未送达」，答辩期限字段为「待定」，重点关注时效起算初判 |

## 错误处理

| 错误情形 | 处理方式 |
|---------|---------|
| 律师无法提供送达日期 | 记录「送达日期待确认」，标记 `[紧急 — 答辩期限需尽快确认]` |
| 时效期间涉及境外法律 | 标记 `[管辖 flagged — 涉外时效，超出中国大陆法律范围]`，不适用民法典第188条 |
| 对方已提出时效抗辩 | 记录时效抗辩存在，标记为高优先级，提示运行 limitation-monitoring 深度分析 |

# 证据保全与种子文档

> 引用规范：`../_shared/legal-basis-conventions.md`

## 目的

在案件录入阶段完成三项关键安排：

1. **外部律师**：记录外部律师/律所的委托状态和联系方式，确保团队协作无盲区
2. **内部负责人**：识别并记录需参与本案的内部利益相关者
3. **证据保全**：确认证据保全通知是否已发出；如未发出且案件为活跃诉讼或合理预期诉讼，触发紧急标记并提供发出选项

**目标**：在录入阶段就锁定关键联系人和证据保全状态，避免后续因联系方式缺失或证据灭失造成的被动局面。

### 2.2 内部负责人清单

| 角色 | 触发条件 | 记录内容 |
|------|---------|---------|
| **业务负责人** | 所有案件 | 姓名 + 联系方式 |
| **HR 合伙人** | 劳动争议案件 | 姓名 + 联系方式 |
| **公关联系人** | 有声誉风险的案件（风险评级高/极高 + 媒体关注可能）| 姓名 + 联系方式 |
| **CISO / 数据合规** | 涉及数据泄露、网络安全、个人信息保护的案件 | 姓名 + 联系方式 |
| **财务负责人** | 重大性为「已计提准备金」或「已披露」的案件 | 姓名 + 联系方式 |
| **其他** | 案件特定需要 | 角色说明 + 联系方式 |

## 步骤三：证据保全

### 3.1 从配置文件读取默认保全策略

从 `litigation-legal/CLAUDE.md` → `## 证据保全` 读取：
- **默认保全触发方式**：自动（每案自动发出）/ 逐案决定（人工评估后触发）
  - 若为「自动」：在步骤 3.2 确认保全状态后，如保全通知尚未发出，直接提示律师立即起草发出（无需额外确认触发）
  - 若为「逐案决定」：在步骤 3.2 确认状态后，仅在律师明确请求时才提示发出；否则仅标记「保全通知待触发」
  - 若字段为 `[PLACEHOLDER]` 或缺失：默认按「逐案决定」处理，提示律师评估是否需要发出
- **默认保全范围**：如「相关业务部门所有与争议相关的文件、邮件、聊天记录」
- **默认刷新周期**：通常为 6 个月
- **保全通知模板位置**：模板路径（如有）

### 3.2 确认证据保全状态

询问律师以下信息：

| 字段 | 说明 |
|------|------|
| **保全通知是否已发出** | 是 / 否 / 不适用（如仲裁尚未启动）|
| 如**已发出**：发出日期 | YYYY-MM-DD |
| 如**已发出**：保全范围 | 涉及的文件类型/系统/时间段 |
| 如**已发出**：保管人 | 收到保全通知的人员姓名列表 |
| 如**已发出**：下次刷新日期 | 默认为发出日 + 6 个月（可调整）|
| 如**未发出**：原因说明 | [律师提供原因]|

### 3.3 未发出保全通知的触发规则

**如果保全通知未发出，且满足以下任一条件：**
- 案件为活跃诉讼/仲裁（已有起诉状或仲裁申请送达）
- 案件为合理预期诉讼（风险评级中等以上 + 有法律威胁信号）

→ 标记 `[证据保全紧急 — 保全通知未发出，合理预期诉讼]`，并提示：

> 建议在录入完成后立即运行 `「legal-hold」（本环境未提供该技能，此步由律师线下执行或跳过） [slug] --issue` 发出证据保全通知。
> 可使用配置文件中的默认保全范围作为起点，根据本案情况定制。

### 3.4 刷新提醒规则

如果已发出保全通知，记录「下次刷新日期」（默认 6 个月后）。在每次 `/matter-update` 中，当距刷新日期 ≤ 30 日时提醒律师刷新保全通知。

> 引用规范：`../_shared/legal-basis-conventions.md`

## 目的

完成案件录入的最后两步：

1. **初始理论**：帮助律师将录入信息整合为一段话的案件框架——我方故事、对方故事、关键事实（pivot fact）和初始立场（fight/settle/investigate/wait）。
2. **装配三件产物**：将所有子技能收集的信息（主体/识别/日期/证据/理论）装配写入 `matter.md`、`history.md` 第零条目、`_log.yaml` 追加行，经律师确认后提交。

**本子技能不决定理论**——它帮助律师组织和表达已有的判断，捕获用户说的内容，不编造。

2. `../_shared/practice-profile-schema.md` — 和解倾向字段映射 + 写入前确认流程
3. 上游子技能产出（如在编排入口下调用）：
   - `subject-conflict-precheck` — 冲突检查结果（状态/路径选择）

## 步骤二：拟定一段话初始理论

向律师询问以下四个要素，帮助整合为一段话框架：

| 要素 | 提问 | 说明 |
|------|------|------|
| **我方故事** | 「从我方角度，这个案件的核心是什么？」| 应能用一两句话表述我方主张的核心事实和法律依据 |
| **对方故事** | 「对方（或对方律师）的核心论点是什么？」| 基于起诉状/仲裁申请或预判；不明确时标记「对方论点待确认」|
| **Pivot fact** | 「这个案件最关键的一个事实是什么？」| 对案件走向影响最大的单一事实（如合同是否有明确约定、是否有书面证据等）|
| **初始立场** | 「你现在的初始立场是什么？」| fight（对抗）/ settle（和解）/ investigate（调查）/ wait（观望）|

**一段话理论格式：**

```
我方故事：[X]。对方故事：[Y]。Pivot fact：[Z]。初始立场：[fight/settle/investigate/wait]。
```

> 所有初始理论均附注：`[需律师确认 — 录入时的理论是工作假设；在任何提交或假设此框架的重大沟通前与外部律师确认]`

## 边界条件

| 情形 | 处理方式 |
|------|---------|
| 律师不愿提供初始理论任何要素 | 记录「律师暂不提供」，允许跳过，在 matter.md 「待决问题」中标记「初始理论待补充」|
| 初始立场与配置文件和解倾向冲突 | 以律师确认的立场为准，在 _log.yaml 中记录律师明确选择 |
| 案件为多方（多原告/多被告）| matter.md 中逐一列出各方当事人，`_log.yaml` counterparty 字段记录主要对方，其余放 name |
| 路径/存储位置未配置（`[PLACEHOLDER]`）| 使用临时默认路径 `matters/[slug]/`，在文件中标记「存储路径需配置后调整」|
| 单独触发（非编排入口调用）| 检查上游信息是否完整；如缺少 subject-conflict-precheck 结果，提示先完成冲突检查 |

## 本技能不做什么

- **不运行冲突检查本身**：冲突检查由 `subject-conflict-precheck` 子技能负责；本技能仅汇总其结果。
- **不决定初始理论**：捕获律师说的内容，不编造或推断。
- **不发出证据保全通知**：标记状态并提供发出选项，实际发出由律师通过 `legal-hold` 技能执行。
- **不分析时效中止/中断**：初判由 `key-dates-limitation` 完成；深度分析由 `limitation-monitoring` 执行。
