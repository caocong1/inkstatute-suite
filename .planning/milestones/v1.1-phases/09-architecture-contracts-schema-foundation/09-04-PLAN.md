# Plan 09-04 - Neutral Boundary Allowlist Gates

## Objective

Convert the neutral package boundary scan from blanket term bans to an allowlist-aware policy that permits legitimate enum/example names while still blocking real coupling, privacy leaks, and legal-only top-level schema fields.

## Threat Model

<threat_model>
<risk id="T-09-04-false-positive" severity="medium">Blanket bans on words like Hermes or WeCom can block legitimate neutral enum values and architecture examples. Mitigation: implement path-aware and schema-field-aware allowlists.</risk>
<risk id="T-09-04-false-negative" severity="high">An allowlist could become too broad and allow private Hermes paths, WeCom payload internals, raw payloads, or secrets. Mitigation: keep hard deny checks for private paths, protocol payload field names, exact `raw_payload` data keys, secret-value patterns, runtime DB/log/media paths, and legal-only top-level required fields.</risk>
<risk id="T-09-04-concrete-package-confusion" severity="medium">Concrete package names may leak into neutral packages outside allowed contexts. Mitigation: allow concrete names only in adapter enum/schema examples, architecture docs, ADRs, and concrete package roots planned for later phases.</risk>
<risk id="T-09-04-existing-test-drift" severity="medium">Updating boundary checks could weaken existing Phase 7 thin-layer tests. Mitigation: preserve existing import/schema tests and add focused allowlist tests for both allowed and forbidden cases.</risk>
</threat_model>
