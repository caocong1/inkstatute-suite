# Plan 93-01: Wave 1 Tracer — apps/web scaffold, Gateway login endpoint, auth flow, home page with conversation list

## Goal

Create the `apps/web` application scaffold and prove the end-to-end vertical slice: login → auth context → home page with conversation list → click a conversation → see workspace shell. This is the minimal tracer that proves the web app builds, the Gateway login endpoint works, the auth flow (cookie-based session) functions, `@solidjs/router` routing works, and `@inkstatute/ui-core` components render in a browser context — all without writing any chat UI code.

The tracer establishes the foundational patterns for the entire phase: (1) the Vite SPA build configuration with `vite-plugin-solid`, dev proxy to Gateway, and `workspace:*` resolution of `@inkstatute/ui-core` and `@inkstatute/platform-sdk-ts`; (2) the `AuthContext` that probes the Gateway for session validity and redirects to `/login` when unauthenticated; (3) the `ConversationContext` that loads the session list from the Gateway and provides `createConversation()` / `refreshConversations()`; (4) the `AdapterContext` with web-specific adapter implementations (FileAdapter, DropAdapter, AppInfoAdapter, WorkspaceAdapter, DocumentParser); (5) the `POST /v1/auth/login` Gateway endpoint that bypasses `require_auth` and issues a session cookie. Once this slice is green, Plans 93-02 through 93-04 expand by wiring the workspace ChatPanel to live SSE, implementing the remaining Gateway stubs, adding responsive mobile layout, and E2E tests.

This plan also adds `apps/web` to the root `package.json` workspaces array and registers a lightweight `web` gate in `scripts/run_v2_gates.py` (typecheck + vitest via a Python wrapper, consistent with the `ui-core` gate pattern). Per AGENTS.md, the gate-coverage meta-test only scans `packages/*/src` and `services/*/src` — `apps/web/src` is not strictly required — but a gate is added for consistency and CI safety.

## Reversibility Gate

**One-way-door: Creating `apps/web` and adding it to root workspaces.** Once `apps/web` is in the `workspaces` array, bun links `@inkstatute/ui-core` and `@inkstatute/platform-sdk-ts` locally. Removing it later would break the workspace graph. Strategy: the addition is purely additive — no existing workspace entry is modified. Task 93-01-01 verifies the scaffold compiles and the gate is additive before building pages on top.

**One-way-door: Adding `POST /v1/auth/login` to the Gateway.** This is a new unauthenticated endpoint that bypasses `require_auth`. The `dispatch()` method in `app.py` currently calls `auth.require_auth(headers)` BEFORE routing to any handler — no bypass exists. Adding a login endpoint means modifying `dispatch()` to skip auth for this specific route. This is security-sensitive: the bypass must be scoped to exactly one route (`POST /v1/auth/login`) and no other. Strategy: the login route is checked BEFORE the `require_auth` call in `dispatch()`, and the handler delegates to a new `GatewayLoginHandler` that calls `GatewaySessionManager.create_session()`. A dedicated test (`test_login.py`) asserts that all other routes still require auth and that the login endpoint rejects invalid credentials when `rbac_enabled=True`.

**One-way-door: AuthContext as the single auth state source.** Once `AuthContext` wraps the router and provides `isAuthenticated()`, all route guards depend on it. Strategy: the context is minimal (session_id, tenant_id, user_id signals + login/logout methods), probes the Gateway on init via `getSession()`, and redirects to `/login` when the probe fails. No localStorage token storage — the HttpOnly cookie is the sole credential.
