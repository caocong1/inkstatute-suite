# Plan 91-04: Skills Endpoint, ChannelAdapter.verify_and_ack Optional Capability, and lawyer-web-chat Deprecation Header

## Goal

Implement three changes that complete the Gateway's capability coverage and the channel protocol evolution:

1. **`GET /v1/skills` endpoint** — proxy to the existing `skill-registry` read API handlers, adding auth and tenant checks. This replaces the 501 stub from Plan 91-01 and satisfies the GW-01 skills endpoint requirement.

2. **`ChannelAdapter.verify_and_ack` optional capability** — add a `verify_and_ack_support: bool = False` field to `ChannelCapabilitySet`, update the `ChannelAdapter` Protocol so `verify_and_ack` is optional (web/desktop adapters do not implement it), and update all existing channel adapters to declare their support level. This satisfies GW-06: "`ChannelAdapter.verify_and_ack` 降级为可选 capability，web / 桌面通道不实现亦合法".

3. **`lawyer-web-chat` deprecation header** — add `Deprecation: true` and `Sunset` headers to all `lawyer-web-chat` responses, marking it as deprecated during the transition period. This satisfies GW-05: "旧服务标记 deprecated".

## Reversibility Gate

**One-way-door:** Making `verify_and_ack` optional on the `ChannelAdapter` Protocol. Once the Protocol is changed, all channel adapters and their tests must be updated. Strategy: the change is additive — a new `verify_and_ack_support: bool = False` field on `ChannelCapabilitySet` (with a default value, so existing code that constructs `ChannelCapabilitySet` without this field still works). The Protocol itself is not changed structurally (Python Protocols don't enforce runtime conformance by default); instead, the `verify_and_ack_support` flag on `ChannelCapabilitySet` declares whether the adapter implements `verify_and_ack`. Adapters that set `verify_and_ack_support = False` are not required to implement `verify_and_ack` meaningfully. A gate test verifies that adapters without `verify_and_ack_support` still pass Protocol validation.

**One-way-door:** Adding deprecation headers to `lawyer-web-chat`. Once the headers are added, clients may begin to rely on them for migration timing. Strategy: the `Sunset` header date is set to a future date (after Phase 95 completion). The headers are additive — no existing response body or status code is changed. `lawyer-web-chat` continues to function during the transition period.

**One-way-door:** The skills endpoint proxies to `skill-registry`'s `handle_get`. Once the Gateway exposes skills at `/v1/skills`, clients will depend on this path. Strategy: the `skill-registry` read API is already proven and feature-flagged. The Gateway adds auth and tenant checks on top, but does not reimplement the skill listing logic.
