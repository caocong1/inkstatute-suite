# Plan 90-01: ACP Event Bridge Tracer — Scaffold Package, Reverse Mapping Core, EventBridge Class, Gate Registration

## Goal

Scaffold the `packages/acp-event-bridge/` package and implement the end-to-end tracer slice: an ACP notification flows through the bridge via forward mapping (reusing `acp-client`'s `map_acp_update_to_run_event`), produces a unified `RunEvent`; a user response flows back through the bridge via reverse mapping, producing a valid ACP JSON-RPC response. This is the minimal vertical slice that proves bidirectional event flow works before expanding into output filtering, privacy scanning, and full roundtrip testing.

The `EventBridge` class integrates the existing forward mapping from `acp-client` with the new reverse mapping, and maintains the `request_id` → unified event correlation needed for JSON-RPC response routing. Gate registration in `scripts/run_v2_gates.py` ensures the new package is CI-covered from the start.

## Reversibility Gate

**One-way-door:** Creating a new `packages/acp-event-bridge/` package and registering its gate in `scripts/run_v2_gates.py`. Once the gate is registered, the `gate-coverage` meta-test will fail if the gate is removed, and the package becomes a permanent CI requirement. Strategy: the gate addition is purely additive — no existing gate entry is modified. The reverse mapping functions are isolated in `reverse_mapping.py` so they can be tested independently of the bridge. Task 01-01 is a checkpoint to verify the package scaffolds, compiles, and the gate registration is additive before building the bridge logic on top.

**One-way-door:** The reverse mapping establishes the JSON-RPC response format for elicitation and permission responses. ACP v1 does NOT use separate methods for user responses — responses are JSON-RPC responses to the original request IDs (see RESEARCH.md §1). Once the response format is locked, changing it would break any caller that constructs responses through the bridge. Strategy: the response format is dictated by the ACP v1 spec (not a design choice), so it is stable by definition. The bridge stores the original `request_id` from each `elicitation/create` and `session/request_permission` notification so responses can be correlated.

2. `map_permission_decision_to_acp(original_request_id: str, outcome: str, option_id: str | None = None) -> dict` — constructs a JSON-RPC response for a permission decision. The response format (from RESEARCH.md §1):
   ```json
   {
     "jsonrpc": "2.0",
     "id": "<original_request_permission_id>",
     "result": {
       "outcome": {
         "outcome": "selected" | "cancelled",
         "optionId": "<selected_option_id>"
       }
     }
   }
   ```
   Parameters: `original_request_id` is the JSON-RPC id from the original `session/request_permission` request. `outcome` must be one of `"selected"`, `"cancelled"` — raise `ValueError` for any other value. `option_id` is the selected option id (only included when `outcome == "selected"`; for `cancelled`, `optionId` is omitted or set to `None`). The function must validate that `outcome` is valid and `original_request_id` is non-empty.

3. `map_run_cancel_to_acp(session_id: str) -> dict` — constructs a `session/cancel` JSON-RPC request (not a response — cancellation is a new request). Format:
   ```json
   {
     "jsonrpc": "2.0",
     "id": "<new_incrementing_id>",
     "method": "session/cancel",
     "params": { "sessionId": "<session_id>" }
   }
   ```
   The `id` field should be a placeholder — the bridge will assign the actual incrementing id when sending. Use `id: None` as a placeholder and document that the bridge replaces it.

4. `map_unified_event_to_acp_response(event_type: str, payload: dict, original_request_id: str) -> dict | None` — dispatcher function that inspects `event_type` and delegates to the appropriate mapping function. For `RunEventType.PERMISSION_REQUESTED.value`-derived responses (when the user provides a permission decision), delegates to `map_permission_decision_to_acp`. For unrecognized event types, returns `None`. The `payload` dict must contain the `action`/`outcome` and `content`/`option_id` fields.
