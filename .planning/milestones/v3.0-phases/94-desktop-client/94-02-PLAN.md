# Plan 94-02: Wave 2 — Workspace SSE wiring, offline SQLite cache, FTS5 workspace search panel

## Goal

Wire the `WorkspacePage` to live Gateway SSE streaming, implement the offline SQLite cache for read-only history, and port the FTS5 workspace search index from `lawyer-desktop`. This plan proves three critical success criteria: (1) the desktop app can send a task to the Gateway and see streaming replies via SSE (same as web — success criterion #6), (2) offline mode shows cached history and artifacts with a clear "需要联网" prompt (success criterion #4), and (3) the FTS5 workspace index works as a desktop-specific enhancement with search results attachable as references (success criterion #5).

The plan reuses the SSE wiring pattern from Phase 93's web client (`SessionContext` + `useEventStream` hook + `EventStreamStore` from ui-core), adapted for the desktop app's signal-based screen switching. The offline cache uses `tauri-plugin-sql` with a separate SQLite database (`offline-cache.db`) for session/run/event metadata, plus filesystem storage for downloaded artifacts. The FTS5 workspace index ports the complete Rust pipeline (scanner → parser → chunker → index_store → manager) from `lawyer-desktop` as Tauri commands, with a new `FTS5SearchPanel` SolidJS component for the search UI.

## Reversibility Gate

**One-way-door: Adding `tauri-plugin-sql` and SQLite databases.** The offline cache and FTS5 workspace index both use SQLite. Once `tauri-plugin-sql` is registered and migrations are defined, the database schema is a structural commitment. Strategy: two separate database files (`offline-cache.db` for history cache, per-root `index.db` for FTS5) keep concerns isolated. Migrations are forward-only and additive.

**One-way-door: FTS5 workspace index as Tauri commands.** The `bind_workspace`, `search_workspace`, and `get_workspace_index_status` commands are desktop-specific and will not be migrated to Gateway. Once registered, they are part of the desktop app's permanent command surface. Strategy: these commands are explicitly called out in UI-05 success criterion #5 as a desktop enhancement — they are intentional, not accidental.

**One-way-door: ConnectionContext as the online/offline state source.** Once `ConnectionContext` wraps the app and provides `connectionState()`, all offline-mode UI depends on it. Strategy: the context is minimal (`"online" | "offline" | "checking"` signal + probe + heartbeat), probes Gateway on launch, and re-probes on network change. Offline mode is read-only — no data is written locally that would conflict with the Gateway on reconnection.

   ```sql
   -- Offline cache for session/run/event metadata (read-only when offline)
   CREATE TABLE IF NOT EXISTS cached_sessions (
       session_id TEXT PRIMARY KEY,
       tenant_id TEXT NOT NULL,
       title TEXT,
       created_at TEXT NOT NULL,
       updated_at TEXT NOT NULL,
       last_viewed_at TEXT
   );

   CREATE TABLE IF NOT EXISTS cached_runs (
       run_id TEXT PRIMARY KEY,
       session_id TEXT NOT NULL,
       status TEXT NOT NULL,
       created_at TEXT NOT NULL,
       completed_at TEXT,
       FOREIGN KEY (session_id) REFERENCES cached_sessions(session_id)
   );

   CREATE TABLE IF NOT EXISTS cached_events (
       event_id TEXT PRIMARY KEY,
       run_id TEXT NOT NULL,
       seq INTEGER NOT NULL,
       event_type TEXT NOT NULL,
       payload_json TEXT NOT NULL,
       occurred_at TEXT NOT NULL,
       FOREIGN KEY (run_id) REFERENCES cached_runs(run_id)
   );

   CREATE TABLE IF NOT EXISTS cached_artifacts (
       artifact_id TEXT PRIMARY KEY,
       run_id TEXT,
       session_id TEXT NOT NULL,
       local_path TEXT NOT NULL,
       kind TEXT,
       name TEXT,
       downloaded_at TEXT NOT NULL
   );

   CREATE INDEX IF NOT EXISTS idx_cached_events_run_id ON cached_events(run_id, seq);
   CREATE INDEX IF NOT EXISTS idx_cached_runs_session_id ON cached_runs(session_id);
   CREATE INDEX IF NOT EXISTS idx_cached_artifacts_session_id ON cached_artifacts(session_id);
   ```
