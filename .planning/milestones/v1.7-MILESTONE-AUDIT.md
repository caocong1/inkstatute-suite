## Critical Gap Details

### Tenant Isolation Not Wired Into Web UIs (HIGH)

**Affected requirements:** TENANT-01, TENANT-02, TENANT-03, TENANT-04

**Root cause:** Phase 56 built tenant isolation primitives (TenantScopeResolver, TenantGuard, TenantScopedContractLogStore, TenantNamespacedCache, Hindsight bank isolation) and verified them at the platform-runtime level. Phase 57 built Web UIs that extract tenant_id from RBAC tokens but do not call TenantGuard.enforce() on read-model queries.

**Evidence:**
- `services/admin-console-api/src/admin_console_api/views.py` — zero tenant references
- `services/admin-web-ui/src/admin_web_ui/server.py:143` — hardcodes `tenant_id="default"`
- `services/lawyer-web-chat/src/lawyer_web_chat/server.py:98` — extracts tenant_id but only passes to session handlers, not TenantGuard

**Impact:** If an operator enables `multi_tenant_enabled=True`, the admin dashboard and lawyer chat would NOT enforce tenant scoping on data access, potentially allowing cross-tenant data leakage.

**Mitigation:** The flag defaults to `False`, so this is a latent gap. The milestone is safe by default. But the requirement text ("every read-model query") is not fully satisfied.

**Recommended fix:** Wire TenantGuard.enforce() into admin-console-api/views.py handlers and pass tenant context from Web UIs through to the read-model layer. This could be a closure phase (e.g., Phase 57.1) or deferred to M4.
