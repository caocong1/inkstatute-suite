## Design System

| Property | Value |
|----------|-------|
| Tool | none (stdlib SSR — not React/shadcn) |
| Preset | not applicable |
| Component library | none — Python `html.escape` string templates in `admin-web-ui` |
| Icon library | none |
| Font | `system-ui, sans-serif` (existing admin dashboard) |

**Stack lock (from research + existing UI):** Extend `services/admin-web-ui` stdlib `http.server` + escaped HTML + CSP. Do **not** introduce React, Vite, Next, or shadcn. The vision config form POSTs through admin-web-ui (CSRF) to `admin-console-api` `PUT /config/vision` (object body with `routing_mode`, `main_model_id`, `vision_model_id`, `vision_provider_id`). The vision probe is a non-destructive POST to `/config/providers/probe` with `target=vision` (Phase 76 probe handler already supports this) that never mutates config and never logs response bodies or resolved secrets. This phase owns the vision config SSR form + nav link; the runtime routing decision logic lives in `platform_runtime/vision_router.py` and is out of UI scope.

## Layout Contract

One single-purpose page inside the existing `.main` → `.section` shell. Do not combine vision config with providers, catalog, or channels on one page (each page has one purpose).

### Vision Config page (`/config/vision`)

```
[InkStatute Admin Dashboard header]
[nav … Channel Config · Provider Config · Model Catalog · Vision Config …]
[identity bar]
[main]
  [section: Vision Config]
    [flash: success | error]          ← only when present
    [probe result block]              ← only when a probe was run this request
    [restart notice]                  ← always visible muted help
    [vision status line]              ← "Vision: …" / "No vision model selected" / "Vision model not required (main only)"
    [card: Routing mode]
      routing-mode <select> (auto | always_preprocess | main_only)
      routing-mode description for the selected mode
    [card: Vision provider and model] ← shown for all modes; fields disabled when main_only
      vision provider <select> (registry provider IDs + blank)
      vision model <select> (built-in catalog models for the selected provider + blank)
      probe button (Probe vision connection)
    [primary CTA: Save vision config]
[/main]
```

Rules:
- Single composition per page: the vision config page is only vision routing. No provider/catalog/channel forms (Phases 75 / 76).
- Cards are interaction containers for the routing-mode group and the vision provider/model group (existing `.card` pattern) — allowed because they group editable fields.
- Max content width remains `1200px` centered (existing `.main`).
- No SPA client routing; full page reload after POST.
- The vision provider/model card is always rendered. When `routing_mode=main_only`, the vision provider/model selects and probe button are rendered `disabled` with the "Vision model not required (main only)" status line — no JavaScript hide/show. The server is authoritative: a `main_only` POST with blank vision fields is valid; a `main_only` POST with vision fields set is accepted but the runtime ignores them (server validation may warn, never error, per draft-tolerant Phase 76 validation).
- No "add" interaction is needed — vision config is a single object, not a list. No JavaScript required for any control.

## Vision Config Interaction Contract (VIS-01)

### Routing mode selector

| Mode | Control | Vision provider/model required | Runtime behavior (informational — runtime owned by `vision_router.py`) |
|------|---------|-------------------------------|--------------------------------------------------------------------------|
| `auto` | `<select>` option `auto` (default selected when stored value is `auto` or unset) | Yes — vision provider + model must be a complete pair | Multimodal main if `supports_vision`; else vision→main mix; else fail-closed notice |
| `always_preprocess` | `<select>` option `always_preprocess` | Yes — vision provider + model must be a complete pair | Always vision→main mix on image-bearing turns |
| `main_only` | `<select>` option `main_only` | No — vision fields disabled and ignored | Never invoke vision; fail-closed notice if main does not support vision |

Display requirements:
1. The routing-mode selector is a `<select>` with a visible `<label for=…>` "Routing mode" (label text inside the `<label>` element — Phase 75 UI-REVIEW fix).
2. The three options appear in fixed order: `auto`, `always_preprocess`, `main_only`. Option text is the exact copy string above (human label, not raw snake_case).
3. Below the select, a Body-text description line shows the exact description copy for the currently selected mode. On a full-page reload after POST, the description reflects the persisted (or submitted) mode. No JavaScript mode-switching is required; if no JS is present, the description matches the server-rendered selected option.
4. When the stored `routing_mode` is `None` (unset), the select defaults to `auto` and the description shows the `auto` description. The POST sends `routing_mode=auto` in that case.
5. The routing-mode select is `disabled` when `operator_config_enabled` is OFF or RBAC denies writes (read-only mode).

### Vision provider and model selection

| Field | Control | Editable | Notes |
|-------|---------|----------|-------|
| `vision_provider_id` | `<select>` of registry provider IDs + a blank "— none —" option | Yes (when mode ≠ `main_only` and flag on) | Defaults to the stored `vision_provider_id` or blank. Built-in vendor IDs (`openai`, `anthropic`) are not valid here — only registry `provider_id` instances. |
| `vision_model_id` | `<select>` of built-in catalog `model_id` values for the selected provider's vendor + a blank "— none —" option | Yes (when mode ≠ `main_only` and flag on) | Defaults to the stored `vision_model_id` or blank. Filtered server-side to models whose `vendor_id` matches the selected provider's `kind`. A custom provider's allowlist models are not in the built-in catalog; for custom providers the select shows only the blank option and a muted help note (see Custom provider note below). |
| `main_model_id` | Hidden input | No | Echoes the stored `catalog.model_id` (the main model) so the API receives a complete `VisionPolicyDoc`. The operator does not edit `main_model_id` here — it is set in Model Catalog. If no main model is selected, the hidden value is blank and the API stores `None`. |

Custom provider note: when the selected `vision_provider_id` resolves to a `custom` provider, the vision model `<select>` shows only the blank option plus a muted note: "Custom provider models are not in the built-in catalog. Add the model ID to the provider's allowlist in Provider Config; vision routing for custom models is not supported in this MVP." This is informational — the operator can still save with a blank vision model (server validation handles completeness).

Display requirements:
1. Both selects have visible `<label for=…>` labels ("Vision provider", "Vision model") with label text inside the `<label>` element.
2. The blank option uses the exact copy "— none —" (em-dash, spaces) as its visible text and an empty string `value=""`.
3. When `routing_mode=main_only`, both selects and the probe button render `disabled`; the vision status line shows "Vision model not required (main only)" in muted `.empty` text.
4. When no providers are configured in the registry, the vision provider `<select>` shows only the blank option and a muted note: "Add a provider in Provider Config before selecting a vision model." The save button remains enabled (a `main_only` save with blank vision is valid); an `auto`/`always_preprocess` save with blank vision is rejected server-side with Error — validation.

### Vision probe (VIS-01, reuses Phase 76 PROV-04 path)

| Concern | Contract |
|---------|----------|
| Trigger | Route-bound form posts to `/config/providers/probe` with `target=vision` plus CSRF. The Phase 76 probe handler resolves the stored `vision_provider_id` / `vision_model_id`; if either is blank, the API returns generic `not_configured` without network access. |
| Mutates config? | No — probe is read-only against the vision provider endpoint; never calls `store.save`. |
| Fail-closed on missing refs | If the vision provider's `api_key_ref` is unset/blank, probe returns the "missing ref" fail copy without making any network call. Never resolves a ref from the environment on the UI side. |
| Logging | Probe result text is generic status only. Never logs the response body, resolved secret, or `Authorization` header. Server logs at most `vision_provider_id` + success/fail boolean. |
| Result display | Probe result renders in a dedicated block above the routing-mode card using `.status-ok` / `.status-err` / `.empty` + the exact copy strings. Result is ephemeral (shown on the re-rendered page after POST; not persisted). |
| RBAC | ADMIN/OPERATOR only; lawyer/viewer denied (match API 403). |
| Flag gate | If `operator_config_enabled` is OFF, probe button is disabled and Error — flag off is shown. Probe does not bypass the flag gate. |
| Disabled when main_only | When `routing_mode=main_only`, the probe button is `disabled` (no vision target to probe). |
| Destination policy | Reuses the Phase 76 probe destination policy verbatim: built-in kinds probe only canonical HTTPS origins; custom probes require HTTPS, reject userinfo and unsafe resolved IP ranges, and do not follow redirects; credentials never cross origins. |

### Submit payload shape

- The vision POST handler builds an object body matching the admin-console-api `PUT /config/vision` allowed keys: `{"routing_mode": "...", "main_model_id": "...", "vision_model_id": "...", "vision_provider_id": "..."}`. Blank selects submit empty strings; the handler normalizes empty strings to `None` before proxying. Do not send raw secret keys (`api_key`, `token`, `password`) — vision config carries IDs only, never refs.
- Server validation (Phase 77 extends `validate.py`): `routing_mode` must be one of `auto` / `always_preprocess` / `main_only`; `vision_provider_id` and `vision_model_id` must be a complete pair or both blank. On reject, show Error — validation copy; do not echo rejected values that look like planted secrets (API already avoids echoing).

## Accessibility & Safety

- Every select and the probe/submit buttons have a visible `<label for=…>` with human text (not raw snake_case). Carried fix from Phase 75 / 76 UI-REVIEW: put the label text inside the `<label>` element so screen readers get an accessible name.
- The routing-mode description line is associated with the routing-mode select via `aria-describedby` pointing at the description element's id, so screen readers announce the selected mode's behavior.
- The vision status line uses `role="status"` so screen readers announce changes after a save/probe re-render.
- Status uses words ("configured" / "not configured" / "not required" / "succeeded" / "failed" / "supported" / "not supported") plus color class — never color alone.
- CSP remains strict (existing server CSP `default-src 'self'; script-src 'self'; style-src 'self'`); no inline scripts; no `innerHTML` of untrusted data — all dynamic strings through `html.escape`. No control on this page requires JavaScript.
- Output boundary (`AdminUiBoundary`) applies to any free-text API messages before render.
- Never render resolved secrets, `.env` file contents, store filesystem paths, probe response bodies, `Authorization` headers, or `api_key_ref` values on this page. Vision config carries IDs only.
- Probe result copy is generic; it never includes HTTP status codes, response snippets, or resolved key material.
- Do not claim live WeCom/QQ acceptance or live vision-model correctness from saving vision config. The fail-closed notice is an InkStatute-owned service notice, not a legal conclusion.
- Reference-first (VIS-03): the UI never asks for or displays raw image bytes. Contract logs store `AttachmentRef.uri` references; the vision config form only selects which provider/model handles image-bearing turns.
