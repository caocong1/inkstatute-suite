# Phase 33: V2 Requirement Audit & Traceability Infrastructure - Plan

**Planned:** 2026-07-03
**Phase:** 33
**Milestone:** v1.5 V2 Acceptance Closure
**Requirements:** AUDIT-01, AUDIT-02, AUDIT-03, AUDIT-04, AUDIT-05, AUDIT-06, AUDIT-07
**Depends on:** Phase 32 (v1.4 completion)

## Goal

Operator can run a deterministic audit that maps every unchecked V2 Active requirement to concrete code evidence and classifies each as satisfied, partial, gap, or human_gate using three-level verification (schema → library surface → production wiring).

## Approach

Build a single stdlib-only audit script (`scripts/audit_v2_requirements.py`) that scans the codebase structure, invokes existing contract-test-suite evidence producers for metadata, and produces a traceability matrix with three-level verification. Extend the V2 gate runner with a 9th gate that fails on gaps. All output is deterministic JSON.

The audit script does NOT re-run tests or gates — it verifies that evidence *exists and is wired*. The gates already prove passing. The audit proves traceability and catches the MEM-07/MEM-16 false-positive pattern (infrastructure present but wiring missing).

## Architecture

```
scripts/audit_v2_requirements.py    (NEW — ~450 lines, stdlib-only)
  ├── RequirementSpec dataclass     (req_id, description, probes, prd_section, human_gate)
  ├── VerificationProbe dataclass   (level, kind, target, checker)
  ├── Three-level verification      (schema → library surface → production wiring)
  ├── Evidence collector            (file paths, test modules, gate names, schema IDs, fixtures)
  ├── Classification engine         (satisfied / partial / gap / human_gate)
  ├── PRD §10 criterion mapper      (§10.1-10.4 → test functions + fixtures)
  ├── JSON sidecar writer           (acceptance/v2-traceability.json)
  └── Gap-check mode                (--check-gaps, exit non-zero on gaps)

scripts/run_v2_gates.py             (MODIFIED — add 9th Gate entry + compileall path)
  └── Gate("v2-acceptance-traceability", (py, "scripts/audit_v2_requirements.py", "--check-gaps"))

acceptance/v2-traceability.json     (NEW — generated by audit script, committed)
  ├── schema_version: "1.0"
  ├── generated_at: <deterministic placeholder>
  ├── requirements: [{ req_id, description, status, evidence: {...}, verification: {...} }]
  └── prd_section_10_mapping: [{ section, criterion, tests, fixtures }]

scripts/audit_v2_requirements.py    (tests — NEW)
  └── tests/test_audit_v2_requirements.py  (stdlib unittest, ~15 test cases)
```

## Tasks

### Task 1: Create audit script core structure (AUDIT-01, AUDIT-06)

**Files:**
- `scripts/audit_v2_requirements.py` (NEW)

**What:**
Create the main audit script with:
- `RequirementSpec` frozen dataclass: `req_id`, `description`, `prd_section`, `human_gate` (bool), `probes` (tuple of `VerificationProbe`)
- `VerificationProbe` frozen dataclass: `level` (1/2/3), `kind` ("schema"/"library"/"wiring"), `target` (str description), `checker` (callable returning bool)
- `REQUIREMENT_REGISTRY`: tuple of 10 `RequirementSpec` entries, one per unchecked V2 Active requirement from PROJECT.md lines 43-52
- `main()` with argparse: `--json` (write sidecar), `--check-gaps` (exit non-zero on gaps), `--requirement REQ_ID` (single-requirement mode), default (print matrix)
- Deterministic output: no timestamps in JSON, sorted keys, stable ordering

**Three-level verification checkers:**
- Level 1 (schema): Check `packages/platform-contract/src/platform_contract/schemas/*.schema.json` contains relevant schema file
- Level 2 (library surface): Use `ast.parse` to verify module exists and contains expected class/function names
- Level 3 (production wiring): Use `re` to scan production entrypoint files (`ingress_runtime.py`, `session_runtime.py`, etc.) for import statements and function calls

**Determinism (AUDIT-06):**
- No `datetime.now()` in output — use a fixed `generated_at: "deterministic"` placeholder
- All lists sorted alphabetically
- `json.dumps(..., indent=2, sort_keys=True)`
- Same input codebase → same output byte-for-byte

**Tests:**
- `tests/test_audit_v2_requirements.py`: test that script runs, produces JSON, is deterministic across two runs

### Task 2: Implement evidence collector (AUDIT-01, AUDIT-02)

**Files:**
- `scripts/audit_v2_requirements.py` (extend Task 1)

**What:**
For each requirement, collect:
- `implementation_files`: Source files that implement the requirement (scanned by probe targets)
- `test_modules`: Test files that cover the requirement (matched by naming convention: `test_phase*.py`, `test_*.py` in relevant service `tests/` dirs)
- `gate_suites`: Gate names from `run_v2_gates.py` that prove the requirement (mapped statically in registry)
- `schema_ids`: Schema file names from `packages/platform-contract/src/platform_contract/schemas/` relevant to the requirement
- `fixtures`: Fixture file paths from `packages/contract-test-suite/fixtures/` and `packages/platform-contract/fixtures/` relevant to the requirement
- `phase_references`: Phase numbers from test file names (e.g., `test_phase5_*` → Phase 5)

Each requirement's `RequirementSpec` includes an `evidence_hints` tuple that guides the collector:
- `source_dirs`: which `services/*/src/*/` or `packages/*/src/*/` dirs to scan
- `test_patterns`: regex patterns for matching test files
- `schema_names`: which schema files are relevant
- `fixture_patterns`: regex patterns for matching fixture files
- `gate_names`: which gates from `run_v2_gates.py` prove this requirement

**Per-requirement evidence bundle** (AUDIT-02):
The JSON sidecar contains a `evidence` object per requirement with all collected paths. The `--requirement REQ_ID` mode prints a detailed bundle for a single requirement.

**Tests:**
- Test that evidence bundles contain expected file paths for known requirements
- Test that `--requirement WECOM` mode prints detailed bundle

### Task 3: Implement three-level verification and classification (AUDIT-03)

**Files:**
- `scripts/audit_v2_requirements.py` (extend Task 1)

**What:**
Classification logic:

```
if requirement.human_gate:
    status = "human_gate"
elif level_1_pass and level_2_pass and level_3_pass:
    status = "satisfied"
elif level_1_pass and level_2_pass and not level_3_pass:
    status = "partial"
else:
    status = "gap"
```

Each requirement's `verification` object in JSON contains:
```json
{
  "level_1_schema": { "passed": true, "evidence": "feedback_event.schema.json exists" },
  "level_2_library": { "passed": true, "evidence": "feedback_service/wecom_normalizer.py: normalize_feedback() found" },
  "level_3_wiring": { "passed": false, "evidence": "ingress_runtime.py does not import wecom_normalizer" }
}
```

**Level 1 checkers** (schema definition):
- Use `pathlib.Path.exists()` to check schema files exist
- Use `json.load()` to verify schema has expected properties

**Level 2 checkers** (library surface):
- Use `ast.parse()` on source files to verify classes/functions exist
- Check for expected method names in class definitions

**Level 3 checkers** (production wiring):
- Use `re.search()` on production entrypoint files for `import` statements
- Verify function calls in entrypoint code paths
- This is the level that catches MEM-07/MEM-16 false-positives

**The 10 requirements and their probe targets:**

| # | Requirement (short) | L1 Schema | L2 Library | L3 Wiring | Human Gate |
|---|---------------------|-----------|------------|-----------|------------|
| 1 | WeCom service | channel_message, channel_delivery | wecom_service/*.py (9 modules) | ingress_runtime.py imports | No |
| 2 | Agent adapter contract | agent_adapter_manifest | agent_backend.py, adapter_manifest.py | ingress_runtime.py uses selector | No |
| 3 | Hermes bootstrap | agent_adapter_manifest | bootstrap.py, adapter_manifest.py | bootstrap health check called | No |
| 4 | Output boundary | — | output_policy.py, owned_notices.py | ingress_runtime.py applies policy | No |

| 8 | Observability/replay/privacy | memory_use, execution_trace | privacy_scan.py, event_stream_replay.py | contract log writer wired | No |

**Tests:**
- Test that a requirement with all 3 levels passing classifies as `satisfied`

**PRD §10 criterion-to-test mapping (AUDIT-07):**
A static `PRD_SECTION_10_MAPPING` tuple in the audit script, with one entry per §10.1-10.4 bullet point. Each entry maps:
- `section`: "10.1", "10.2", "10.3", or "10.4"
- `criterion`: The acceptance criterion text (from V2-PRD.md)
- `tests`: List of test function names or test module paths that prove this criterion
- `fixtures`: List of fixture file paths that exercise this criterion
- `gate`: Which V2 gate suite enforces this in CI

The mapping is derived from V2-PRD.md §10.1-10.4 (lines 588-640) cross-referenced with the actual test modules and fixtures found in RQ-3/RQ-7.

- Also prints summary to stdout
- Deterministic: sorted keys, no timestamps

## Risks

1. **Risk: Three-level verification probes may be too brittle** — if production wiring paths change, probes break. **Mitigation:** probes check for import patterns, not exact line numbers; tests verify probes pass against current codebase.

2. **Risk: Audit script may classify a genuinely-satisfied requirement as `partial`** — if the wiring path is non-obvious. **Mitigation:** Phase 33 classifies honestly; Phase 34 closes partials. `partial` is not a failure for the 9th gate.

3. **Risk: PRD §10 mapping may miss criteria** — V2-PRD.md is in Chinese, criteria are nuanced. **Mitigation:** mapping is reviewed against the PRD text; tests verify all 4 sections are covered.

4. **Risk: Determinism may break if file system ordering varies** — `Path.iterdir()` order is not guaranteed. **Mitigation:** all lists are sorted before JSON serialization.
