<objective>
Implement and test the approval security three-state policy required by DSH-04.

The three states are: (1) unknown permission kind → auto-deny (never shown to user), (2) terminal/execute_code kind → render user card (deferred decision for UI), (3) no batch approval path exists anywhere. This is a critical security requirement — the approval stack is the only interaction channel (DP-3) and unknown kinds must never be surfaced.

Purpose: Lock down the approval security boundary before any UI is built (Phase 116). The policy logic is testable in isolation with mock permission events.
Output: `approval_policy.dart` with `ApprovalPolicy` class + comprehensive three-state test coverage.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Permission policy → ACP server | Policy decisions are sent back to the engine as JSON-RPC responses; the engine acts on them (tool execution proceeds or is blocked) |
| Engine → permission policy | Untrusted tool call metadata arrives via session/request_permission; the policy must not execute code or trust tool call content |
