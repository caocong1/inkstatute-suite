# Plan 93-03: Wave 2 — Gateway stub implementations + elicitation/approval + upload/artifact/feedback wiring in web client

## Goal

Implement the 5 remaining Gateway stub endpoints (`get_session`, `list_session_runs`, `get_run`, `submit_elicitation`, `submit_approval`) and wire the complete lawyer flow in the web client: upload attachment → send task → answer clarification card → download artifact → submit feedback. After this plan, the full desktop browser flow (success criterion #2) is functional end-to-end.

The Gateway currently has 5 endpoints returning `_not_implemented` stubs (app.py lines 194-203). The web client's success criteria require these to work — without `get_session`, the auth probe can't verify session validity; without `list_session_runs`, the conversation list can't show history; without `submit_elicitation`, clarification cards can't be submitted; without `get_run`, run status can't be polled. This plan implements all 5 stubs with real handlers that delegate to the `GatewaySessionManager`, `RunRuntime`, and a new `GatewayElicitationHandler` / `GatewayApprovalHandler`.

On the web client side, this plan wires: (1) file upload via `gateway.upload()` with the `webFileAdapter`; (2) `ClarificationCard` submission to `gateway.submitElicitation()` (now functional); (3) artifact download via `gateway.getArtifact()` with the `webFileAdapter.saveFile()`; (4) `MessageFeedback` submission to `gateway.submitFeedback()` (already functional from Phase 91); (5) the conversation list loading from `gateway.listSessionRuns()` / `gateway.getSession()` (now functional).

## Reversibility Gate

**One-way-door: Implementing Gateway stub endpoints.** The 5 stub endpoints become real handlers. Once implemented, the web client depends on their response shapes. Strategy: each handler is implemented in a dedicated module (`sessions.py` extension, `runs.py`, `elicitation.py`, `approvals.py`) with clear response contracts. The response shapes match the existing OpenAPI document — no schema changes. Tests assert the response shape for each endpoint.

**One-way-door: Elicitation/approval flow as the single clarification path.** Once `submit_elicitation` is wired, the `ClarificationCard` → Gateway → agent resume flow is the only clarification path. Strategy: the `SessionContext.submitClarification()` method (from Plan 93-02) already calls `gateway.submitElicitation()` — this plan makes the Gateway side functional. The web client code doesn't change shape, only the Gateway response changes from 501 to 200.
