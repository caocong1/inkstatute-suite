# Plan 43-02 — Fixture-Driven QQBot Channel Loop Proof + Idempotency + Feedback Source Mapping

## Goal

Prove the QQBot ChannelAdapter portability end-to-end with a fixture-driven loop: receive → ACK → adapter (normalize) → reply (text deliver) → card (card deliver) → feedback (FeedbackEvent). Then prove idempotency (repeat `verify_and_ack` + `normalize_inbound` with the same raw → same `idempotency_key` and `turn_id`). Finally, prove that `FeedbackEvent.source` maps to the existing `CARD_BUTTON` enum value without adding new enum values.

This plan satisfies:
- QQBOT-03: fixture-driven QQBot loop proof showing receive → ACK → adapter → reply → card → FeedbackEvent end-to-end with idempotency, proving ChannelAdapter portability beyond WeCom.
- QQBOT-04: QQ Bot feedback maps to existing `FeedbackEvent.source` enum values (CARD_BUTTON) without adding new enum values.

## Context

- Plan 43-01 (Wave 1) created the `packages/channel-core/` shared package with extracted channel-generic logic and the `packages/channels/qqbot/` package with `QQBotChannelAdapter` implementing all 6 `ChannelAdapter` Protocol methods. This plan builds on top of that structure.
- The `QQBotChannelAdapter` already implements `channel_id`, `capabilities`, `verify_and_ack`, `normalize_inbound`, `deliver`, and `health` (created in Task 43-01-03).
- The adapter imports from `channel_core`, `platform_contract`, and `platform_runtime` only — NOT from `wecom_service` (verified by Task 43-01-04).
- The closest reference pattern for a fixture-driven loop proof is `packages/channels/web_sse/fixtures/multichannel_web_sse.json` — a self-contained JSON fixture with inbound, agent_turn, delivery, feedback callback, feedback event, capabilities, and health sections.
- `FeedbackSource` enum (defined in `packages/platform-contract/src/platform_contract/enums.py:132-136`) has 4 values: `CARD_BUTTON`, `TEXT_COMMAND`, `WEB_FORM`, `ADMIN_ANNOTATION`. QQBot card button feedback maps to `CARD_BUTTON` ("card_button"). No new enum values may be added (contract freeze SAFETY-02, SAFETY-06).
- `Channel.QQBOT = "qqbot"` already exists in `packages/platform-contract/src/platform_contract/enums.py:35`.
- Contract freeze (SAFETY-02, SAFETY-06): No changes to `packages/platform-contract/` or `packages/platform-runtime/protocols.py` or `packages/platform-runtime/src/platform_runtime/feature_flags.py`.
- Privacy: No literal secrets in fixture or test files. Use `REDACTED` or short placeholders (< 12 chars). The privacy scanner scans `.planning/phases/**/*.md`.

<objective>
Operator can run three test modules that prove:
1. The full QQBot channel loop (receive → ACK → normalize → text deliver → card deliver → feedback normalize) works end-to-end via a self-contained JSON fixture with no network IO.
2. Repeated `verify_and_ack` and `normalize_inbound` calls with the same `RawInbound` produce identical `idempotency_key` and `turn_id` values (idempotent).
3. `FeedbackEvent.source` for QQBot feedback maps to the existing `CARD_BUTTON` enum value, and the `FeedbackSource` enum still has exactly 4 values (no new values added).
</objective>
