# Plan 103-02: ACP Server Entry Point

## Objective

Implement `inkstatute-agent acp` — a CLI entry point that speaks ACP v1 over stdio, allowing the agent-core to be driven by any standard ACP client (including the platform's own `ACPBackendAdapter`). This proves the self-built core has no architectural privilege — it can be used in-process OR as an ACP subprocess, just like Hermes.

## Files to Create

### `packages/agent-core/src/inkstatute_agent_core/acp_server.py`
ACP server protocol handler. Reads JSON-RPC 2.0 from stdin line-by-line, responds over stdout.

**Protocol methods:**
1. **`initialize`** → respond with:
   - `protocolVersion: 1`
   - `agentInfo: {name: "inkstatute-agent", version: "0.1.0"}`
   - `capabilities: {streaming: true, elicitation: true, permissions: true}`
   - Does NOT declare `fs/*` or `terminal/*`
2. **`session/new`** → create session, respond with `sessionId`
3. **`session/prompt`** →
   - Extract text from prompt content blocks
   - Build messages list
   - Create EventEmitter + model provider
   - Start `run_turn()` async generator
   - Map each `RunEvent` → ACP `session/update` notification (reverse mapping)
   - When turn completes, respond with empty result
4. **`session/cancel`** → cancel the running turn, respond
5. **`session/close`** → clean up session, respond

**Reverse event mapping (RunEvent → ACP session/update):**
- `message.delta` → `{type: "agent_message_chunk", content, messageId}`
- `message.completed` → `{type: "agent_message", content, messageId}`
- `thought.delta` → `{type: "agent_thought_chunk", content}`
- `tool_call.started` → `{type: "tool_call_update", toolCallId, toolName, status: "started"}`
- `tool_call.delta` → `{type: "tool_call_update", toolCallId, content}`
- `tool_call.completed` → `{type: "tool_call_update", toolCallId, status: "completed"}`
- `plan.updated` → `{type: "plan", plan}`
- `phase.changed` → `{type: "plan", plan}` (fold into plan update)
- `error` → `{type: "error", message}`
- `elicitation.requested` → `elicitation/create` request (agent-side)
- `permission.requested` → `session/request_permission` request (agent-side)

**Elicitation agent-side:**
When the turn loop emits `elicitation.requested`, the ACP server sends an `elicitation/create` request to the client and waits for the response. The response is fed back into the turn loop.

**Permission request agent-side:**
When the turn loop emits `permission.requested`, the ACP server sends a `session/request_permission` request to the client. The client's decision is fed back. Dangerous permissions (`terminal`, `execute_code`) are never auto-approved.

## Implementation Details

### ACP Server Architecture
The server uses `asyncio` to handle the async turn loop while reading from stdin. The main loop:
1. Read line from stdin (sync, blocking — in a thread executor)
2. Parse JSON-RPC message
3. Dispatch to handler
4. For `session/prompt`: run `run_turn()` async generator, map events to notifications, write to stdout

### Stdin/Stdout Handling
- Read: `sys.stdin` line-by-line (use `asyncio.to_thread` for async compatibility)
- Write: `sys.stdout.write(json.dumps(msg) + "\n"); sys.stdout.flush()`
- Same pattern as `echo_agent.py` fixture

### Session Management
- In-memory dict: `sessions: dict[str, SessionState]`
- `SessionState` holds: session_id, messages, active turn task, event buffer
- Sessions are independent — no cross-session state

### --check Flag
`inkstatute-agent acp --check`:
1. Try to create a model provider from config
2. If successful: print "InkStatute ACP check OK", exit 0
3. If failed: print error, exit 1
Matches `hermes acp --check` pattern.

### Integration Test
The final test (`test_acp_server_can_be_driven_by_acp_client`) uses the existing `ACPClient` from `packages/acp-client/` to drive the agent-core ACP server. This proves the server is a standard ACP agent.
