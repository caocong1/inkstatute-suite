### Task 97-01-02: Implement Hermes materializer (symlink-first, copy for scripts/)

**Action**: Implement `hermes_materializer.py` with the `materialize_hermes()` function and `HermesMaterializer` class. The materializer reads `skill-index.json`, resolves source paths, and produces a Hermes profile layout under `output_dir/profiles/<profile>/skills/<skill-name>/`. For skills without `scripts/` directories, create symlinks to the source SKILL.md directory. For skills with `scripts/`, use `shutil.copytree`. Fall back to copy if symlink fails (cross-filesystem). Log the strategy used per skill.

**Files to create/modify**:
- `packages/skill-materializer/src/inkstatute_skill_materializer/hermes_materializer.py` (full implementation)
- `packages/skill-materializer/tests/test_hermes_materializer.py`
- `packages/skill-materializer/tests/fixtures/` (minimal SKILL.md fixtures)

**Read first**:
- `packages/skill-index/src/inkstatute_skill_index/index_builder.py` (IndexRecord fields: skill_id, name, source_repo, plugin, relative_path, required_scripts, content_hash)
- `solutions/lawfirm/src/inkstatute_solutions_lawfirm/hermes_materializer.py` (V2 materializer pattern — reference only, not reused)
- `.planning/phases/97-skill-materialization/97-CONTEXT.md` §1 (Hermes profile layout, symlink naming convention)
- `.planning/phases/97-skill-materialization/97-RESEARCH.md` §1 (profile directory structure, symlink vs copy strategy, HERMES_HOME integration)

**Acceptance criteria**:
- [ ] `materialize_hermes(index_path, output_dir, profile_name)` produces `output_dir/profiles/<profile>/skills/<skill-name>/SKILL.md` for each skill in the index
- [ ] Skills without `scripts/` directories are symlinked to source repo paths (zero-copy)
- [ ] Skills with `scripts/` directories are copied via `shutil.copytree` with a `.sync_source` marker file
- [ ] Symlink naming convention: `<plugin-prefix>-<skill-name>` for ai-for-china-legal, `legal-<skill-name>` for legal-skills
- [ ] Falls back to `shutil.copytree` if `os.symlink` raises `OSError` (cross-filesystem or permissions)
- [ ] Returns a `MaterializationResult` with: `materialized_count`, `symlinked_count`, `copied_count`, `fallback_count`, `errors` list, `strategy_log` (per-skill strategy used)
- [ ] Read-only on source repos: test asserts source repo file mtimes and content hashes are unchanged after materialization
- [ ] Fixture-based unit tests pass: minimal SKILL.md fixtures → materialize → assert symlink/copy structure

### Task 97-01-03: Implement host assumption rewriter (pattern-based, deterministic, auditable)

**Action**: Implement `host_assumption_rewriter.py` with the `HostAssumptionRewriter` class. Apply three deterministic regex-based transformation rules to SKILL.md body text: (1) `/plugin:skill` trigger patterns → natural language trigger description, (2) `ask_user`/`ask-user` → `elicitation`, (3) `CLAUDE.md` references → flagged but not rewritten. Each rewrite is logged in a `RewriteReport` with `original_text`, `rewritten_text`, `rule_applied`, `location` (file path + line number).

**Files to create/modify**:
- `packages/skill-materializer/src/inkstatute_skill_materializer/host_assumption_rewriter.py` (full implementation)
- `packages/skill-materializer/tests/test_host_assumption_rewriter.py`
- `packages/skill-materializer/tests/fixtures/rewriter_fixtures.py` (SKILL.md snippets with known patterns)

**Read first**:
- `packages/skill-index/src/inkstatute_skill_index/metadata_extractor.py` (trigger pattern regex `_TRIGGER_PATTERN`, gate pattern detection)
- `.planning/phases/97-skill-materialization/97-CONTEXT.md` §9 (host assumption rewriting rules)
- `.planning/phases/97-skill-materialization/97-RESEARCH.md` §3 (rewriting rules, prevalence data, rewrite report structure)

**Acceptance criteria**:
- [ ] `HostAssumptionRewriter.rewrite(text, file_path)` returns `(rewritten_text, RewriteReport)`
- [ ] Rule 1: `/commercial-legal:risk-identification` → natural language like "When the user asks about risk-identification..." (deterministic, no LLM)
- [ ] Rule 2: `ask_user` and `ask-user` → `elicitation` (simple text substitution, case-insensitive)
- [ ] Rule 3: `CLAUDE.md` references are flagged in the report as `practice_profile_dependency` but NOT rewritten in the text
- [ ] `RewriteReport` contains a list of `RewriteEntry` records with: `original_text`, `rewritten_text`, `rule_applied`, `location` (file path + line number)
- [ ] Deterministic: same input → same output (no random, no LLM, pure regex)
- [ ] Reversible: the report contains enough information to reconstruct the original text
- [ ] Edge cases handled: patterns inside code blocks are still rewritten (documented behavior); false positives are logged for review
- [ ] Unit tests with fixture SKILL.md snippets covering all three rules pass

### Task 97-01-05: Implement three-separation routing manifest producer

**Action**: Implement `three_separation.py` with the `produce_routing_manifest()` function. Given a `skill-index.json`, produce a metadata-only routing manifest (JSON) containing only index-level fields needed for routing: `skill_id`, `name`, `description`, `token_estimate`, `declared_gates`, `host_assumptions`, `required_scripts`, `source_path` (for on-demand body reading). No skill body text is included. This enforces the metadata/body/tools separation principle.

**Files to create/modify**:

**Acceptance criteria**:
- [ ] `produce_routing_manifest(index_path, output_path)` writes a JSON file with metadata-only skill records
- [ ] Each record contains: `skill_id`, `name`, `description`, `token_estimate`, `declared_gates`, `host_assumptions`, `required_scripts`, `source_path`, `skill_type`, `parent_skill`
