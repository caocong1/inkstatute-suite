# Plan 40-01 — Provider Model Adapter Package Structure, Manifest, and Capability Probe

<objective>
Create the `packages/backends/provider_model/` package mirroring the Codex adapter structure, implement `ProviderModelBackendAdapter` with all 9 `BackendAdapter` Protocol methods, build `AgentBackendManifest` with `production_ready: false`, `no_channel_io: true`, and `invocation_mode="direct_llm"`, and implement the `ProviderModelCapabilityProbe` returning a 14-field `AdapterCapabilitySet`.

This plan satisfies ADAPTER-02 Success Criteria 1:
- SC1: `agent_backend.mode=provider_model` routes to a provider_model adapter returning a valid `AgentBackendManifest` with `production_ready: false` and `invocation_mode="direct_llm"`.
</objective>

## Context

- The `BackendAdapter` Protocol (9 methods) is frozen at `packages/platform-runtime/src/platform_runtime/protocols.py:222-239`.
- `AdapterCapabilitySet` (14 fields) is frozen at `packages/platform-contract/src/platform_contract/agent_adapter.py:18-33`.
- `AgentBackendMode.PROVIDER_MODEL` already exists at `agent_adapter.py:15` — no enum change needed.
- The runtime selector at `services/wecom-service/src/wecom_service/agent_backend.py:23-56` already routes by mode and validates manifests — no selector changes needed.
- The Codex adapter at `packages/backends/codex/` is the structural template (Phase 39 shipped complete).
- `provider_model_backend_enabled` feature flag exists at `packages/platform-runtime/src/platform_runtime/feature_flags.py:25` (default False).
- The adapter must NOT import `platform_runtime` concrete backends or `openai` at module top level — preserve the thin-layer boundary and lazy SDK import.
- `production_ready: false` — this is a prototype, not production-ready.
