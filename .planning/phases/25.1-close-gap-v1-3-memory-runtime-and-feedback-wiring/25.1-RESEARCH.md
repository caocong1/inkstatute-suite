## User Constraints (from CONTEXT.md)

### Locked Decisions
## Implementation Decisions

### Runtime Memory Wiring
- Ordinary WeCom continue/start flows must be able to invoke platform memory recall before backend submission.
- The integration must preserve interrupt resume and active-task fast-path behavior from the existing WeCom session runtime.
- Context passed to backend submission must remain bounded and reference-first: memory refs, rolling summary refs, feedback correction refs, artifact refs, and output-policy refs only.
- Backend gateway/meta/session commands must not leak to ordinary lawyer users.

### Feedback-to-Memory Wiring
- Feedback callbacks may create same-session correction refs and pending memory candidates only through privacy-safe, reference-first metadata.
- High-risk legal conclusions, route mismatch, skill candidates, and skill changes must remain human-reviewed and `no_auto_modify`.
- Approved candidates may enter durable recall only through explicit review actions; rejected or deferred candidates must not enter recall.
- Service-level feedback wiring must stay backend-neutral and InkStatute-owned.

### Evidence and Failure Behavior
- `MemoryUse` evidence failure must not be silently ignored in legal production mode.
- The caller must receive fail-closed behavior or explicit degraded status metadata when evidence cannot be recorded.
- Contract logs and memory evidence must avoid raw callback bodies, legal/customer full text, document text, and secrets.
- Evaluation and fixture evidence must remain synthetic or sanitized.

### Verification Closure
- Produce or normalize validation artifacts for phases 22, 23, 24, and 25.
- Produce `VERIFICATION.md` for phases 20, 21, 22, 23, 24, and 25 after closure work is in place.
- Update requirement traceability only when verification evidence exists.
- The v1.3 milestone audit must be rerunnable and no longer report critical runtime/feedback wiring gaps.

### the agent's Discretion
Implementation details are at the agent's discretion when they preserve the V2 platform contract, InkStatute-owned WeCom boundary, privacy rules, and existing codebase patterns.

## Summary

Phase 25.1 should be planned as a narrow closure phase, not a new memory subsystem. The existing `MemoryOrchestrator`, `ContextAssembler`, `FeedbackLearningPolicy`, `InMemoryMemoryCandidateReviewStore`, `MemoryCandidateReviewDecider`, and `SQLiteMemoryStore` already exist and are exported from `platform_runtime`; the missing work is service/runtime wiring plus evidence policy hardening. [VERIFIED: codebase grep]

The correct runtime integration point is `WeComSessionRuntime.handle_turn()` after session resolution has chosen `CONTINUE_SESSION` or `START_NEW_SESSION` and before `runtime.create_run(...)`; interrupt resume and active-task follow-up must continue to bypass create-run memory recall. [VERIFIED: services/wecom-service/src/wecom_service/session_runtime.py] `WeComRuntimeIngress.handle_callback()` builds the `RunRequest` metadata and delegates to `WeComSessionRuntime`, so ingress should inject the same optional memory dependencies instead of implementing a parallel callback path. [VERIFIED: services/wecom-service/src/wecom_service/ingress_runtime.py]

Feedback wiring should live in `services/feedback-service` as dependency-light helper code that normalizes/dedupes/classifies events, calls `FeedbackLearningPolicy.learn(...)`, queues pending candidates, persists candidate rows when a durable store is injected, and returns safe same-session correction refs for future context assembly. [VERIFIED: services/feedback-service/src/feedback_service/queue.py; packages/platform-runtime/src/platform_runtime/memory.py] High-risk route/skill evidence is already classified as human-review and `no_auto_modify`; the plan should preserve that behavior and add service-level tests proving it. [VERIFIED: services/feedback-service/src/feedback_service/classification.py; packages/platform-runtime/src/platform_runtime/memory_review.py]

**Primary recommendation:** Add optional, host-injected memory and feedback learning ports around existing runtime/service classes; do not add a daemon, provider SDK, Hermes-core change, new database, or raw payload storage. [CITED: AGENTS.md; VERIFIED: codebase grep]

## Architecture Patterns

### System Architecture Diagram

```text
WeCom callback
  -> normalize_wecom_turn()
  -> WeComRuntimeIngress.handle_callback()
  -> RunRequest(metadata refs only)
  -> WeComSessionRuntime.handle_turn()
       -> validate scope
       -> resolve_session_turn()
       -> if pending interrupt: runtime.resume_interrupt()
       -> else if active task: route_active_task_turn()
       -> else continue/start:
            optional MemoryOrchestrator.recall_and_assemble()
            -> MemoryStoreAdapter.search()
            -> ContextAssembler.assemble()
            -> record MemoryUse according to evidence policy
            -> attach context bundle refs/status to RunRequest.metadata
            -> runtime.create_run()

Feedback callbacks / FeedbackEvent inputs
  -> normalize_feedback_inputs()
  -> dedupe_feedback_events()
  -> classify_feedback_event()
  -> FeedbackLearningPolicy.learn()
       -> feedback_correction_refs for same-session context
       -> pending MemoryCandidate entries for repeated negative feedback
       -> route/skill candidates marked human-review/no_auto_modify
  -> queue candidates / optionally upsert durable candidates
  -> human MemoryCandidateReviewDecider action
       -> approve/edit/tombstone writes MemoryRecord
       -> reject/defer does not create recall-visible memory
```

The diagram reflects existing call boundaries and the proposed optional memory injection point. [VERIFIED: codebase grep]

### Pattern 1: Optional Pre-Create Memory Recall

**What:** Add `memory_orchestrator: MemoryOrchestrator | None = None` to `WeComSessionRuntime` and `WeComRuntimeIngress`, then call it only for `CONTINUE_SESSION` and `START_NEW_SESSION` before `runtime.create_run`. [VERIFIED: services/wecom-service/src/wecom_service/session_runtime.py]

**When to use:** Use when the host provides a platform-native memory store/summary store; if omitted, behavior remains current. [VERIFIED: packages/platform-runtime/src/platform_runtime/memory_orchestrator.py]

**Example:**

```python
# Source: services/wecom-service/src/wecom_service/session_runtime.py and
# packages/platform-runtime/src/platform_runtime/memory_orchestrator.py
decision_request = _run_request_for_decision(run_request, decision=decision)
if self.memory_orchestrator is not None:
    result = self.memory_orchestrator.recall_and_assemble(
        scope=scope,
        session_id=str(decision.session_id),
        turn_id=str(getattr(turn, "turn_id")),
        current_turn_ref=str(decision_request.metadata["current_turn_ref"]),
        current_turn_text=str(getattr(turn, "content", "") or ""),
        recent_turn_refs=tuple(decision_request.metadata.get("recent_turn_refs", ())),
        artifact_refs=tuple(decision_request.metadata.get("artifact_refs", ())),
        feedback_correction_refs=tuple(decision_request.metadata.get("feedback_correction_refs", ())),
        output_policy_ref=decision_request.metadata.get("output_policy_ref"),
    )
    decision_request = replace(
        decision_request,
        metadata=_safe_json({
            **decision_request.metadata,
            "context_bundle_id": result.bundle.context_bundle_id,
            "memory_refs": result.bundle.memory_refs,
            "summary_ref": result.bundle.summary_ref,
            "feedback_correction_refs": result.bundle.metadata.get("feedback_correction_refs", []),
            "memory_recall_status": "ok",
        }),
    )
run = await self.runtime.create_run(decision_request)
```

### Pattern 2: Evidence Failure Policy

**What:** Replace unconditional swallow of `record_memory_use` exceptions with a policy value such as `evidence_failure_mode = "fail_closed" | "degraded" | "ignore_if_unsupported"`. [VERIFIED: packages/platform-runtime/src/platform_runtime/memory_orchestrator.py]

### Anti-Patterns to Avoid

- **Calling memory recall before interrupt/active-task routing:** This would add unnecessary work and can break existing fast-path behavior. [VERIFIED: services/wecom-service/tests/test_session_interrupt_runtime.py]
- **Adding memory to `DefaultRunRuntime`:** Existing tests assert this constructor remains memory-free. [VERIFIED: packages/platform-runtime/tests/test_memory_orchestrator.py]
- **Passing raw feedback messages or callback bodies into memory metadata:** Feedback queue and memory validators reject `raw_payload` and unsafe text keys; keep refs/hashes/lengths only. [VERIFIED: services/feedback-service/src/feedback_service/queue.py; packages/platform-runtime/src/platform_runtime/memory.py]
- **Auto-promoting route/skill candidates:** `MemoryCandidateReviewDecider` only permits defer for `review_route_or_skill_candidate`. [VERIFIED: packages/platform-runtime/src/platform_runtime/memory_review.py]
- **Treating Phase 25 external spikes as live adapter integration:** Audit says Phase 25 simulations are acceptable for spike scope only. [CITED: .planning/v1.3-MILESTONE-AUDIT.md]

## Common Pitfalls

### Pitfall 1: Breaking Interrupt Resume

**What goes wrong:** Memory recall runs before a pending interrupt is resumed, or modifies the `RunRequest` used by `resume_interrupt`. [VERIFIED: services/wecom-service/src/wecom_service/session_runtime.py]
**Why it happens:** The create-run and resume paths share the same `handle_turn()` entry point. [VERIFIED: services/wecom-service/src/wecom_service/session_runtime.py]
**How to avoid:** Inject recall only after `decision.action` is known and only in the final continue/start branch. [VERIFIED: services/wecom-service/src/wecom_service/session_runtime.py]
**Warning signs:** `runtime.created` is non-empty in pending clarification tests, or `runtime.resumed` changes. [VERIFIED: services/wecom-service/tests/test_ingress_runtime.py]

### Pitfall 2: Failing Open on MemoryUse Evidence

**What goes wrong:** A broken evidence sink still returns a usable context bundle with no visible warning. [VERIFIED: packages/platform-runtime/src/platform_runtime/memory_orchestrator.py]
**Why it happens:** Current code catches all exceptions from `record_memory_use` and ignores them. [VERIFIED: packages/platform-runtime/src/platform_runtime/memory_orchestrator.py]
**How to avoid:** Add policy-driven `fail_closed` or `degraded` behavior and assert it in orchestrator and WeCom runtime tests. [CITED: .planning/phases/25.1-close-gap-v1-3-memory-runtime-and-feedback-wiring/25.1-CONTEXT.md]
**Warning signs:** Tests still describe skipped evidence as acceptable for stores that claim `record_memory_use`. [VERIFIED: packages/platform-runtime/tests/test_memory_orchestrator.py]

### Pitfall 3: Metadata Shape Drift

**What goes wrong:** WeCom runtime attaches `context_bundle` objects or raw text instead of refs/status fields. [ASSUMED]
**Why it happens:** `ContextAssemblyResult.as_event()` contains a structured bundle, but backend submission metadata should remain bounded and reference-first. [VERIFIED: packages/platform-runtime/src/platform_runtime/context_assembler.py; CITED: .planning/phases/25.1-close-gap-v1-3-memory-runtime-and-feedback-wiring/25.1-CONTEXT.md]
**How to avoid:** Attach only `context_bundle_id`, `memory_refs`, `summary_ref`, `feedback_correction_refs`, `artifact_refs`, `output_policy_ref`, `estimated_tokens`, `dropped_sections`, and status metadata. [VERIFIED: packages/platform-runtime/src/platform_runtime/context_assembler.py]
**Warning signs:** `_safe_json` rejects metadata due to `full_text`, `document_text`, `raw_payload`, or similar keys. [VERIFIED: services/wecom-service/src/wecom_service/session_runtime.py]

### Pitfall 4: Feedback Candidate Promotion Without Review

**What goes wrong:** Callback handling writes `MemoryRecord` directly from negative feedback. [ASSUMED]
**Why it happens:** Feedback learning produces memory candidates, but the review decider is a separate step. [VERIFIED: packages/platform-runtime/src/platform_runtime/memory.py; packages/platform-runtime/src/platform_runtime/memory_review.py]
