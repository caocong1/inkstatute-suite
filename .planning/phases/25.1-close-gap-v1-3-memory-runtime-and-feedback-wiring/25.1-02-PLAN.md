<objective>
Close the FBL service wiring gap by connecting the existing feedback-service callback ingestion path to platform feedback learning, same-session correction-ref persistence, and human review surfaces without adding a new service, database, queue, provider, or Hermes dependency.

Purpose: Phase 23 produced feedback learning and review primitives, but the v1.3 audit found feedback-service code does not invoke them and same-session corrections do not feed future context. This plan updates the service ingestion orchestration to call `wire_feedback_to_memory(...)`, persist safe correction refs into an injected store, queue candidate rows when stores are injected, and keep explicit review actions separate from callback ingestion.

Output: `feedback_service.memory_wiring` helper/context-store module, a `queue.py` ingestion API that calls it, public exports, and tests proving callback ingestion correction persistence, next-context retrieval compatibility, pending candidates, explicit review promotion, rejection/defer behavior, and no-auto-modify route/skill safety.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Feedback callback/event input -> feedback-service ingestion | Untrusted feedback event mappings enter normalization, dedupe, classification, and learning. |
| Existing feedback ingestion -> feedback-service helper | Normalized callbacks are handed to feedback memory wiring. |
| Feedback-service helper -> platform-runtime learning policy | Sanitized event metadata becomes correction refs and pending candidates. |
| Feedback-service helper -> feedback memory context store | Same-session correction refs are stored for next runtime context assembly. |
| Feedback-service helper -> review store/durable candidate store | Pending candidates are queued or persisted as candidates only. |
| Explicit review action -> memory store | Human review decisions can promote approved candidates to MemoryRecord entries. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-25.1-05 | Tampering | `ingest_feedback_callback_for_memory` and `wire_feedback_to_memory` | mitigate | Existing callback/service ingestion calls the wiring helper, stores refs, queues candidates, and never calls `memory_store.upsert()` or promotes recall-visible memory. |
| T-25.1-06 | Elevation of Privilege | route/skill candidate review | mitigate | Preserve `proposed_action="review_route_or_skill_candidate"` guard; tests assert only defer is allowed and no-auto-modify remains true. |
| T-25.1-07 | Information Disclosure | feedback event metadata | mitigate | Reuse feedback queue clone/privacy checks and platform memory safe metadata; reject raw payload/full-text keys. |
| T-25.1-08 | Repudiation | duplicate feedback callbacks | mitigate | Use existing dedupe/idempotency metadata and return queued candidate ids plus persisted candidate ids in result metadata. |
| T-25.1-SC | Tampering | npm/pip/cargo installs | mitigate | No package install is planned; all code uses existing stdlib/local packages. |
</threat_model>
