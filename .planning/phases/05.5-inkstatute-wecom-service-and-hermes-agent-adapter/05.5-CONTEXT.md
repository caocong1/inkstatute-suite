<domain>
## Phase Boundary

Phase 5.5 builds the minimum InkStatute-owned WeCom receive/send service and the backend-neutral agent adapter boundary required before live WeCom acceptance can proceed. It must prove that ordinary lawyer users talk to InkStatute WeCom service, that Hermes is used only as the first agent backend, and that Hermes gateway/meta/update/command/system notices cannot leak to ordinary WeCom users.

This phase may add `services/wecom-service/`, agent adapter contract/config/manifest artifacts, Hermes adapter/bootstrap evidence under `services/hermes-contract-layer/`, output policy code/tests, sanitized profile bundle manifests, compatibility matrix docs, and contract-test-suite fixtures. It must not rebuild Hermes core, Hermes router, session storage, skill registry, MCP registry, model gateway, full feedback/read APIs, full multi-channel gateway, production Codex/provider-model adapters, runtime databases, queues, secrets storage, or automatic legal skill modification.

</domain>

<decisions>
## Implementation Decisions

### InkStatute WeCom Service Boundary

- **D-01:** Create the target ordinary-user channel boundary under `services/wecom-service/`. Hermes gateway is migration/operator evidence only and must not be the V2 ordinary lawyer WeCom receive/send path.
- **D-02:** The WeCom service owns callback receipt, signature/decryption hooks where required, retry dedupe, 5-second ACK behavior, inbound normalization, outbound send envelope construction, media reference handling, feedback callback receipt, send retries, delivery error normalization, and idempotency.
- **D-03:** ACK and normalization are separate from agent reasoning. The service must ACK or produce a channel-level error without waiting for Hermes agent execution; long or async work is represented through contract events/status and later push messages.
- **D-04:** Normalize WeCom text, file, image, voice, and button callback inputs into existing platform contract shapes: `AgentTurn` for user tasks and `FeedbackEvent` for card/button feedback. Use `raw_payload_ref`, media refs, and sanitized metadata instead of raw callback bodies or customer legal text.
- **D-05:** Prefer stdlib and dependency-light implementation. If real WeCom AES decrypt support requires a crypto dependency, the plan must justify and isolate that dependency specifically for WeCom protocol handling.

### Agent Backend Adapter Contract and Runtime Selector

- **D-06:** Define `agent_backend.mode` with `hermes`, `codex`, and `provider_model`; Phase 5.5 production readiness is required only for `hermes`. `codex` and `provider_model` remain schema/config-compatible future modes and must be covered by non-Hermes synthetic tests, not runtime implementations.
- **D-07:** Adapter manifests must declare adapter name/version, backend version, profile/bundle identity, hook/event support, invocation mode, sync/async behavior, feedback target support, session read support, artifact return support, trace support, and `no_channel_io`.
- **D-08:** Adapter input and output must map through platform events and service envelopes: `AgentTurn` in; `AgentResult`, `ExecutionTrace`, artifacts, feedback references, and route metadata out. Legal-only fields stay under `industry_context` or metadata.
- **D-09:** The runtime selector must refuse or block live acceptance when the selected adapter cannot satisfy `no_channel_io` or when it can only complete the ordinary WeCom flow by using Hermes gateway as the user channel.

### Hermes Adapter Bootstrap and Compatibility

- **D-10:** Extend `services/hermes-contract-layer/` as the Hermes adapter/bootstrap surface. Do not edit Hermes core or commit files from `/home/sorawatcher/.hermes`.
- **D-11:** Provide a non-mutating Hermes capability probe and compatibility matrix that record verified Hermes source/version, hook/event capability, agent invocation capability, profile path expectation, contract log path expectation, config switches, known gateway direct-send paths to avoid, and version-drift fallback behavior.
- **D-12:** Support two bootstrap narratives: reuse an existing Hermes install by probing/linking a supported lawfirm profile, and reproduce on a new server from a sanitized lawfirm profile bundle or bundle manifest.
- **D-13:** The sanitized profile bundle must include structure, SOUL/profile references, hooks, skill/MCP/script references, adapter config, and required external env/secret names only. It must exclude WeCom keys, callback tokens, encoding AES keys, model keys, runtime DBs, logs, feedback payloads, customer documents, media files, and raw legal payloads.
- **D-14:** If Hermes version drift removes required hook/invocation behavior, the adapter must report unsupported or fallback status explicitly; it must not silently route ordinary WeCom users back through Hermes gateway.

### Assistant Output Boundary

- **D-15:** Implement output policy at the InkStatute WeCom service send boundary. Hermes `response_filter` can be an input signal, but it is not the channel boundary.
- **D-16:** The policy must allow legal business replies, clarifying questions, business progress/status updates, files/artifacts, template cards, feedback cards, and InkStatute-owned maintenance notices.
- **D-17:** The policy must block or rewrite Hermes/gateway lifecycle notices, update/self-update prompts, slash command/help/status/credits/insights notices, memory/tool progress, dangerous command approval text, delivery failure debug details, `ADMIN_NOTICE`, stack traces, internal paths, commands, tokens, env/profile/runtime details, and other backend operator UI text before ordinary WeCom delivery.
- **D-18:** Rewrites must use InkStatute-owned service language such as service maintenance or delivery status notices. Do not semantically rewrite legal conclusions, citations, factual assumptions, risk judgments, jurisdiction conclusions, liability conclusions, or user-provided case facts.
- **D-19:** Output policy evidence should be privacy-safe and auditable. Unless a later plan explicitly changes platform schemas, keep output-policy audit as service-local sanitized records or metadata rather than inventing a sixth top-level platform contract event.

### Evidence, Testing, and Live Acceptance Gate

- **D-20:** Local tests must cover WeCom callback verification/decryption fixtures where feasible, ACK timing, retry dedupe, inbound normalization, feedback callback idempotency, outbound send envelope construction, output policy allow/block/rewrite behavior, no-secret logging, and no-channel-io adapter manifests.
- **D-21:** Contract-test-suite fixtures must include non-Hermes synthetic adapter cases so platform core does not couple to Hermes paths, hook names, profile layout, lawfirm-only fields, or WeCom-only assumptions.
- **D-22:** Live WeCom acceptance remains blocked until evidence shows ordinary users receive messages from InkStatute WeCom service, Hermes is used only for agent logic, feedback callbacks are captured by InkStatute WeCom service, and output policy prevents Hermes meta/gateway/update/command notices from reaching ordinary users.
- **D-23:** Fixtures can prove local behavior but cannot be labeled live acceptance. Runtime credentials, callback bodies, contract logs, customer documents, media files, feedback payloads, and raw legal payloads must stay outside the repo.
- **D-24:** High-risk legal feedback remains human-reviewed. Phase 5.5 may record `skill_candidate` evidence through existing contract fields, but must not call skill optimization runners or auto-modify legal conclusion skills.

### the agent's Discretion

- The planner may choose exact module boundaries inside `services/wecom-service/`, provided the service stays minimal and owns only the V2 WeCom channel responsibilities.
- The planner may decide whether adapter manifests live under `packages/platform-contract/`, `services/hermes-contract-layer/`, or both, as long as the backend-neutral contract is testable and Hermes-specific details do not leak into platform core.
- The planner may choose fixture names, helper script names, and evidence document names. Prefer names that make fixture, migration, and live evidence impossible to confuse.
- The planner may defer real live WeCom runs behind explicit blocked evidence if runtime secrets, WeCom callback access, or safe sanitized samples are unavailable.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets

- `platform_contract.events` and JSON schemas already define the `AgentTurn`, `AgentResult`, `FeedbackEvent`, `ExecutionTrace`, and `RouteDecision` shapes that WeCom service and adapters should produce or consume.
- `platform_contract.enums` already includes WeCom channel, text/file/image/voice/button callback message types, status update reply type, and feedback/card button enum values needed by Phase 5.5.
- `contract_test_suite.event_stream_replay` can validate event-stream envelopes and relationship integrity for result-side streams.
- `hermes_contract_layer.hook` already protects Hermes outbound context and records only when a contract log path or writer is configured.
- `hermes_contract_layer.mapper` already maps Hermes `agent:end` context to the four core events with `message_id` as optional feedback target and `raw_payload_ref` privacy defaults.
- `hermes_contract_layer.wecom_validation` already checks fixture evidence for WeCom channel, ACK timing, feedback target presence, and raw payload/secret-like leakage.
- `feedback_service.wecom_normalizer` already demonstrates sanitized feedback normalization, repeated callback collapse, route-mismatch skill candidates, and no-auto-modify metadata.

### Established Patterns

- Contract-adjacent packages are Python-first and dependency-light; tests use stdlib `unittest`, `json`, `pathlib`, temporary files, and explicit `PYTHONPATH`.
- Fixtures are synthetic or sanitized and must use `fixture://` or `raw_payload_ref` references. Runtime logs, callback bodies, customer documents, secrets, feedback payloads, and media files stay outside the repo.
- Phase 5 work clearly separates fixture validation from live acceptance; Phase 5.5 must preserve that separation and update evidence only when the InkStatute WeCom service path is proven.
- Current Hermes contract layer is a shadow recorder and adapter surface, not a replacement for Hermes core or a user-facing gateway.

### Integration Points

- New service target: `services/wecom-service/`.
- Hermes adapter/bootstrap target: `services/hermes-contract-layer/` plus sanitized bundle/manifest docs or fixtures.
- Existing result log env var: `INKSTATUTE_CONTRACT_LOG_PATH`.
- Existing feedback compatibility inputs: sanitized `feedback.jsonl` and `pending_previews.jsonl` examples, treated as migration inputs only.
- Contract-test-suite fixtures/tests are the natural place to prove adapter composability, no-Hermes-coupling, output policy, and WeCom callback/send-envelope behavior before CI wiring in Phase 7.

</code_context>

<specifics>
## Specific Ideas

- Prefer first plans that establish testable contracts before live/protocol depth: WeCom service skeleton and output policy fixtures, then adapter manifests/runtime selector, then Hermes bootstrap matrix/bundle evidence, then end-to-end fixture/live gate.
- Prefer explicit terms in evidence docs: `fixture_passed`, `live_blocked`, `live_passed`, `no_channel_io_verified`, and `output_boundary_verified`.
- Prefer output policy fixtures named around blocked notice families: gateway lifecycle, self-update, slash command/help/status/credits/insights, memory/tool progress, delivery debug, stack trace/internal path/token, and allowed legal business reply.
- Prefer adapter manifest tests that include one non-Hermes synthetic adapter so Phase 5.5 does not accidentally define Hermes as the platform contract.
- Prefer WeCom callback fixtures with redacted fields and `raw_payload_ref` identifiers rather than copied callback XML/JSON.

</specifics>
