# Phase 5.5 Research: InkStatute WeCom Service and Hermes Agent Adapter

## RESEARCH COMPLETE

## Research Summary

Phase 5.5 should be planned as a service-and-boundary phase, not as a Hermes runtime rebuild. The current repo already has platform contract schemas, contract-test-suite replay helpers, Hermes shadow recording, WeCom fixture validation, and a minimal sanitized feedback normalizer. The missing V2 acceptance layer is InkStatute-owned WeCom receive/send plus a backend-neutral agent adapter contract with Hermes as the first production adapter.

The plan should prioritize testable local behavior first: callback verification and ACK helpers, idempotency, inbound normalization into `AgentTurn` / `FeedbackEvent`, outbound send envelopes, output policy allow/block/rewrite decisions, adapter manifest/schema/selector, no-channel-io enforcement, Hermes compatibility/bundle evidence, and fixture-backed end-to-end replay. Live WeCom acceptance remains a manual/operator gate because it requires secrets, connected WeCom runtime, Hermes runtime access, and sanitized live evidence outside the repo.

## Key Findings

### Existing Assets

- `packages/platform-contract/src/platform_contract/events.py` already defines the event dataclasses that Phase 5.5 should use.
- `packages/platform-contract/src/platform_contract/enums.py` already includes `wecom`, text/file/image/voice/button callback message types, `status_update`, and feedback enums.
- `packages/contract-test-suite/src/contract_test_suite/event_stream_replay.py` validates event-stream envelopes and relationship integrity.
- `services/hermes-contract-layer/src/hermes_contract_layer/hook.py` records safely without mutating outbound Hermes context.
- `services/hermes-contract-layer/src/hermes_contract_layer/mapper.py` maps Hermes `agent:end` context, including optional `message_id` feedback target and reference-first privacy metadata.
- `services/hermes-contract-layer/src/hermes_contract_layer/wecom_validation.py` validates fixture evidence for WeCom channel, ACK timing, feedback target, and raw payload/secret leakage.
- `services/feedback-service/src/feedback_service/wecom_normalizer.py` already normalizes sanitized compatibility feedback JSONL into schema-valid `FeedbackEvent` records.

### Implementation Approach

- Add `services/wecom-service/` as a small Python package with no default runtime server dependency. The first implementation should expose pure functions/classes that can be tested without network calls: protocol verification, callback normalization, idempotency keys, send envelopes, output policy, and adapter dispatch contracts.
- Add backend-neutral adapter manifest bindings and validation before Hermes-specific bootstrap details. This prevents Hermes-specific paths or hook names from becoming platform contract assumptions.
- Treat Hermes bootstrap as evidence and compatibility tooling: manifest, capability probe, compatibility matrix, sanitized profile bundle manifest, and health checks. Do not copy live Hermes profile content or secrets into the repo.
- Implement output policy at WeCom service send boundary. `response_filter` is useful but insufficient because Hermes gateway/update/restart/delivery/status paths can bypass `agent:end`.
- Keep live acceptance evidence separate from fixture tests. Local fixture tests can pass while `live_wecom_status` remains `blocked`.

### Dependency Notes

- Most Phase 5.5 code can remain stdlib-only.
- Real WeCom AES-CBC callback decryption may need a crypto dependency. The plan should isolate this as a justified protocol dependency if implemented; otherwise it should provide a decrypt interface and fixture tests without adding broad dependencies.
- No new database or queue is required for Phase 5.5 local evidence. Idempotency can be modeled as pure keys and in-memory/test stores; production persistence can be deferred unless explicitly required by live deployment.

### Security and Privacy Risks

- WeCom callback bodies, media files, AES keys, tokens, secrets, runtime logs, and customer legal materials must never be committed.
- Output policy must not rewrite legal conclusions, citations, facts, risk judgments, jurisdiction conclusions, or liability conclusions.
- Adapter `no_channel_io` is a live acceptance gate. If Hermes can only complete the ordinary WeCom loop through Hermes gateway, the selected mode must be marked unsupported for V2 live acceptance.
- Sanitized lawfirm bundle artifacts must be manifests/templates only, with external env/secret names and no raw profile runtime data.

## Validation Architecture

### Automated Validation

- WeCom protocol and normalization unit tests under `services/wecom-service/tests/`.
- Output policy tests covering allow, block, rewrite, legal-conclusion pass-through, and secret/internal-path detection.
- Adapter manifest schema/dataclass tests under `packages/platform-contract/tests/` and contract-test-suite tests with a non-Hermes synthetic manifest.
- Runtime selector tests that reject adapters with `no_channel_io=false`.
- Hermes bootstrap tests that run against temporary/synthetic profile directories and never mutate `/home/sorawatcher/.hermes`.
- Contract-test-suite fixture tests for `AgentTurn -> AgentResult -> FeedbackEvent` through InkStatute WeCom service + Hermes adapter envelopes.

### Manual / Operator Validation

- Live short legal retrieval task through InkStatute WeCom service.
- Live long/document task through InkStatute WeCom service.
- ACK timing from live service, text/file/card delivery from InkStatute send boundary, feedback callback captured by InkStatute callback route, and contract log reference outside the repo.
- Operator confirmation that ordinary WeCom users did not see Hermes gateway/update/command/meta notices.

### Pass / Block Rules

- Local fixture and unit tests may mark `fixture_status: passed`.
- `live_wecom_status` remains `blocked` until the live operator evidence exists.
- Missing WeCom credentials, unavailable callback access, unavailable Hermes agent invocation evidence, unsafe samples, or output policy gaps must be recorded as blockers, not treated as passing acceptance.

## Planning Recommendation

Use four plans:

1. WeCom service protocol, normalization, send envelopes, and output policy.
2. Agent adapter contract, manifest schema, and runtime selector.
3. Hermes adapter bootstrap, compatibility matrix, and sanitized bundle manifest.
4. End-to-end fixture/live evidence gate for InkStatute WeCom service + Hermes agent adapter.

This ordering lets the executor build the user-channel boundary before depending on Hermes-specific bootstrap evidence, while still keeping Phase 5.5's live gate honest.
