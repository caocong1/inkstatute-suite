## Data Flow Pattern

```text
WeCom callback
  -> protocol verification/decrypt abstraction
  -> idempotency key
  -> AgentTurn or FeedbackEvent normalization
  -> runtime selector
  -> Hermes adapter receive_turn
  -> AgentResult / ExecutionTrace / artifacts
  -> output policy
  -> WeCom send envelope
  -> template card feedback callback
  -> FeedbackEvent
```

All raw callback, media, customer, and legal payloads remain represented by references such as `raw_payload_ref`, `media_ref`, or runtime-owned paths outside the repo.

## Testing Pattern

- Use `unittest`, `json`, `pathlib`, and temporary directories.
- Keep import paths explicit with `PYTHONPATH=...`.
- Test pure functions first; do not require a dev server or live WeCom runtime.
- Use `rg`/source assertions for docs/evidence checks when behavior is documentation-only.
- For privacy, recursively reject exact `raw_payload` keys and secret-like strings in fixtures/evidence.

## Boundary Pattern

- Platform contract code may define adapter-neutral manifests and schemas.
- `services/wecom-service/` owns ordinary-user WeCom channel behavior and output policy.
- `services/hermes-contract-layer/` owns Hermes adapter/bootstrap evidence and shadow contract integration.
- `services/feedback-service/` remains minimal compatibility normalization until Phase 6; do not expand it into APIs or queues in Phase 5.5.
