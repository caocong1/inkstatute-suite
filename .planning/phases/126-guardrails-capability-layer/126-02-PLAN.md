- **action:** 在 `legal-core` 预设的人设中写入六段护栏指令（其余分域预设继承 core）。
  人设必须包含以下**可被门禁 grep 的锚点标记**：

```
[GUARDRAIL:RESEARCH_GATE]
在对任何法律问题下结论之前，你必须先检索现行有效的法律、行政法规、司法解释或指导性案例。
未经检索不得给出结论性意见；若无法检索，明确说明"未经检索，以下仅为初步分析方向"。

[GUARDRAIL:CITATION_AUDIT]
每一处法律依据都必须标注来源等级：
- verified：你已检索并核对原文
- retrieved：检索到但未核对原文
- unverified：凭记忆或推断，未经检索
格式：在引用后紧跟 `[verified]` / `[retrieved]` / `[unverified]`。禁止省略。

[GUARDRAIL:ASK_USER]
当关键事实缺失、直接影响结论方向时，不得起草、不得下结论。
改为输出澄清块，格式严格如下：
[CLARIFY:
Q1: <问题>
- <选项A>
- <选项B>
Q2: <问题>
]
澄清块之外不要再输出结论。

[GUARDRAIL:DE_AI_POLISH]
终稿须经润色：去除"首先/其次/综上所述"式套话、去除对用户显而易见的解释、
使用中国法律实务文书的行文习惯。避免机器翻译腔与列表堆砌。

[GUARDRAIL:HUMAN_REVIEW]
以下情形必须在结论处标注 `[HUMAN_REVIEW: <原因>]`：
诉讼时效认定、合同效力认定、刑事责任判断、金额超过 100 万的条款意见、
涉及行政处罚幅度、任何你标注为 unverified 依据支撑的结论。
该标记不得因用户要求而移除。

[GUARDRAIL:CONFIDENTIALITY]
处理客户材料前提醒用户：内容将发送至第三方模型 API。
不要在回答中复述完整的当事人姓名、身份证号、联系方式、银行账号。

[SKILL_LOADING]
动手之前，先用 skill 工具按名加载与本任务法律领域对应的技能。
不要凭记忆作答已有技能覆盖的任务。
```

**注意**：`[GUARDRAIL:*]` 锚点是给门禁 grep 用的，模型看到也无妨。

### Task 2: 渲染侧 —— 文本约定的派生事件

- **type:** code
- **files:** apps/desktop/src-tauri/src/engine/guardrails.rs, apps/desktop/src-tauri/src/engine/mapper.rs
- **action:** 实现从已提交 assistant 文本派生护栏事件：

```rust
/// 从一段已提交文本中扫出护栏相关结构。
pub struct GuardrailScan {
    pub citations: Vec<Citation>,
    pub clarification: Option<ClarificationRequest>,
    pub human_review: Vec<HumanReviewMark>,
}
pub struct Citation { pub text: String, pub level: CitationLevel, pub offset: usize }
pub enum CitationLevel { Verified, Retrieved, Unverified }
pub struct HumanReviewMark { pub reason: String, pub offset: usize }

pub fn scan(text: &str) -> GuardrailScan;
```

**解析规则，逐条落实：**

1. **引用等级**：正则匹配 `\[(verified|retrieved|unverified)\]`，取其**前面**最近的一段文本作为引用体
   （向前找到最近的句号/换行为界，上限 200 字符）。

2. **澄清块**：严格块状格式，**必须有闭合 `]`**：
   ```
   \[CLARIFY:\s*\n(.*?)\n\s*\]
   ```
   块内按 `Q<数字>:` 切问题，每问题下以 `- ` 开头的行为选项。
   **无闭合括号则不识别**（防止正文里出现 `[CLARIFY:` 字样时误伤）。
   解析结果映射到 ui-core 既有的 `ClarificationRequest` / `ClarificationQuestion` 契约。

3. **人审标记**：`\[HUMAN_REVIEW:\s*([^\]]+)\]`，捕获原因。

4. 在 `mapper.rs` 的 `message.completed` 分支里调用 `scan`，为每条 citation 产一条
   `citation.recorded`，为澄清块产一条 `elicitation.requested`，
   人审标记放进 `message.completed` 的 `metadata.human_review`。

5. **GRD-11 research-gate 的可核验化**：映射器维护「本轮是否出现过检索类 `tool_call.started`」
   （工具名匹配 `web_search` / `fetch` / `read` / 含 `search` 的技能工具），
   放进 `run.state_changed` 的 `metadata.research_performed: bool`。
   前端在无 verified 引用**且** `research_performed == false` 时渲染"待核实"标记。

- **verify:**
  - 单元测试：三种引用等级各一例，含中文标点边界
  - 单元测试：`[CLARIFY:` 无闭合 → 不识别（负例，防误伤）
  - 单元测试：`[CLARIFY:` 完整块 → 正确解析 2 问 4 选项
  - 单元测试：正文里出现字面量 "[HUMAN_REVIEW" 但无闭合 → 不识别
  - 单元测试：`research_performed` 在有/无检索工具调用时分别为 true/false
- **acceptance_criteria:** 解析器有负例保护，不误伤正文

### Task 3: 批准卡片组件

- **type:** code
- **files:** apps/desktop/src/components/PermissionCard.tsx, apps/desktop/src/components/PermissionCard.css
- **action:** 新建组件（ui-core 无此组件，属 app 层）：
  - 输入：`permission.requested` 事件的 payload（工具名、参数摘要、options）
  - 渲染：工具名 + 请求内容摘要 + **两个按钮：允许一次 / 拒绝一次**
  - **绝对禁止**：任何"总是允许"、"全部批准"、"记住选择"的入口
  - 点击后调用 `engineRespondPermission(requestId, allow)`
  - 卡片在应答后转为已决状态（显示"已允许"/"已拒绝"），不可再点
  - 超时兜底：60 秒未操作则自动拒绝并显示"已超时，已自动拒绝"
  - 样式用 `molv-tokens.css` 变量，与 ChatPanel 的卡片风格一致
- **verify:**
  - 测试：渲染后 DOM 中恰有 2 个按钮
  - 测试：`grep -in "总是\|always\|全部\|batch\|记住" PermissionCard.tsx` 无命中
  - 测试：点击"允许"调用 `engineRespondPermission(id, true)`
  - 测试：60 秒后自动拒绝（用 fake timers）
- **acceptance_criteria:** 无批量批准路径，超时安全拒绝

- **action:**
