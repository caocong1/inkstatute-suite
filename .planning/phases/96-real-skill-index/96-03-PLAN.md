# Plan 96-03: Dual-Repo Merge + Conflict Model

## Goal

Build the dual-repo merge and conflict classification layer on top of the scanner core from Plan 96-01. This plan implements:

1. **Namespace isolation** — `ai-for-china-legal` skills use `<plugin>:<skill>` namespacing; `legal-skills` skills get `legal-` prefix (inherited from `sync_legal_skills.py`'s `local_dir_name()` function). The namespace mapping are recorded in the merge report.

2. **4-state conflict classification** — `in-sync` / `upstream-changed` / `both-changed` / `local-missing` — inherited from `lawfirm-profile/scripts/sync_legal_skills.py` semantic, adapted to the index level (read-only, no filesystem sync).

3. **Merge report generation** — produces the `merge_report` section of `skill-index.json` with `namespace_mapping` and `conflict_classification`.

This plan depends on Plan 96-01 (scanner core produces `ScannedSkill` records with skill_ids). It can run in parallel with Plan 96-02 (classification + metadata) since they touch different new files. Both plans modify `__init__.py` but with different symbols (additive, no conflict).

## Reversibility Gate

**One-way-door:** Adding `conflict_model.py` to the `inkstatute_skill_index` package. This is a new module — purely additive. The conflict model is read-only (produces a report, does not sync files). If the model is wrong, the module can be modified without affecting the scanner or classifier. No existing file is modified except `__init__.py` (additive exports).

<action>
Create `packages/skill-index/src/inkstatute_skill_index/conflict_model.py`.

This module implements the dual-repo merge and conflict model. It inherits the 4-state classification semantic from `sync_legal_skills.py` but adapts it to the index level (read-only, no filesystem sync).

Define the following:

1. A frozen slotted dataclass `ConflictEntry` with fields:
   - `skill_id: str` — the skill's namespace-prefixed ID
   - `status: str` — one of `"in-sync"`, `"upstream-changed"`, `"both-changed"`, `"local-missing"`
   - `content_hash: str` — SHA-256 hash of the SKILL.md content (current scan)
   - `previous_hash: str | None` — SHA-256 hash from previous index (None if skill is new)
   - `has_local_modification: bool` — whether a local modification marker was detected
   - `version: str | None` — version from frontmatter (if available)

2. A frozen slotted dataclass `MergeReport` with fields:
   - `namespace_mappings: dict[str, str]` — mapping from original skill name to namespace-prefixed ID (e.g., `{"court-sms": "legal-court-sms", "contract-review": "commercial-legal:contract-review"}`)
   - `conflict_classification: dict[str, list[str]]` — dict with keys `"in-sync"`, `"upstream-changed"`, `"both-changed"`, `"local-missing"`, each mapping to a list of skill_ids
   - `total_skills: int` — total number of skills in the merge
   - `summary: dict[str, int]` — count per status: `{"in-sync": N, "upstream-changed": N, "both-changed": N, "local-missing": N}`

3. A function `compute_content_hash(text: str) -> str`:
   - Returns `hashlib.sha256(text.encode("utf-8")).hexdigest()`

4. A function `build_namespace_mappings(skills: list[ScannedSkill]) -> dict[str, str]`:
   - For each skill, maps the raw `name` (from frontmatter or directory) to the `skill_id` (namespace-prefixed)
   - For legal-skills: `{"court-sms": "legal-court-sms", "de-ai-polish": "legal-de-ai-polish"}`
   - For ai-for-china-legal: `{"contract-review": "commercial-legal:contract-review"}`
   - For shared: `{"cn-law-research-gate": "shared:cn-law-research-gate"}`
   - Handles the `local_dir_name()` quirk from sync_legal_skills.py: if a skill name already starts with `legal-`, the namespace ID is `legal-<name>` (doubling the prefix, matching the sync script's behavior). This is documented as a known quirk.

5. A function `classify_conflicts(current_skills: list[ScannedSkill], previous_index: dict[str, Any] | None = None) -> list[ConflictEntry]`:
   - For each skill in `current_skills`:
     - Compute `content_hash` from `skill.raw_text`
     - If `previous_index` is None or skill_id not in previous index → `status = "local-missing"` (new skill, auto-add)
     - If skill_id in previous index:
       - Get `previous_hash` from previous index record
       - Get `has_local_modification` from previous index record (if available)
       - If `content_hash == previous_hash` and not `has_local_modification` → `status = "in-sync"`
       - If `content_hash == previous_hash` and `has_local_modification` → `status = "in-sync"` (local meta-only is treated as in-sync at index level; the sync script's `local-meta-only` state is collapsed into `in-sync` for the 4-state model)
       - If `content_hash != previous_hash` and not `has_local_modification` → `status = "upstream-changed"`
       - If `content_hash != previous_hash` and `has_local_modification` → `status = "both-changed"`
     - Extract `version` from `skill.frontmatter` if available
   - Returns list of `ConflictEntry` for all skills

6. A function `build_merge_report(skills: list[ScannedSkill], previous_index: dict[str, Any] | None = None) -> MergeReport`:
   - Calls `build_namespace_mappings(skills)` to get namespace mappings
   - Calls `classify_conflicts(skills, previous_index)` to get conflict entries
   - Groups skill_ids by status into `conflict_classification` dict
   - Computes `summary` counts
   - Returns `MergeReport`

7. A helper function `_load_previous_index(path: Path) -> dict[str, Any] | None`:
   - If path exists, reads and JSON-parses the previous index file
   - Returns `None` if file doesn't exist or is invalid
   - The previous index is expected to have a `skills` array with records containing `skill_id`, `content_hash`, and optionally `has_local_modification`

8. A helper function `_detect_local_modification(skill: ScannedSkill) -> bool`:
   - Checks for local modification markers:
     - A `.local_modification` marker file in the skill directory (read-only check, does not create)
     - A `LOCAL_CHANGELOG.md` file in the skill directory (inherited from sync_legal_skills.py's `LOCAL_CHANGELOG_SUFFIX`)
   - Returns `True` if any marker is found, `False` otherwise
   - This is a read-only filesystem check — uses `Path.exists()`, never creates files

Import `ScannedSkill` from `.scanner`. Import `hashlib`, `json` from stdlib. Import `Path` from pathlib. Import `Any` from typing. Import `dataclass`, `field` from dataclasses.

CRITICAL: The conflict model is READ-ONLY. It produces a report, it does NOT sync files. No `shutil.copytree`, no `git checkout`, no file writes. The `_detect_local_modification` function only checks for marker file existence — it never creates markers. The 4-state classification is output as a merge report in the index, not used for filesystem operations. The `local-meta-only` and `missing-upstream` extra states from sync_legal_skills.py are not used in the 4-state model (they are collapsed into `in-sync` and omitted respectively, as per the requirements which specify exactly 4 states).
</action>
