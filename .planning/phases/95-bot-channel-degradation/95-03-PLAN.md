# Plan 95-03: QQ Bot Full Migration — Gateway Client + Event Consumer + Keyboard Cards

## Goal

Create the Gateway client and event consumer for the QQ bot service (mirroring the WeCom pattern from Plans 95-01/95-02), then switch the QQ bot post-ACK composition path from direct agent calls to the Gateway event consumer. The QQ event consumer maps `BotDelivery.cards` to QQ feedback keyboards (via `build_feedback_keyboard_envelope()`), maps `BotDelivery.files` to QQ rich media delivery, and handles QQ-specific concerns: passive reply window checking, scene-aware delivery (c2c vs group), and wakeup path.

After this plan:
- QQ webhook → verify_and_ack (ED25519, op=13) → post-ACK → GatewayClient.create_run → SSE stream → aggregate_events → adapter.deliver
- No `runtime.create_run()` or `backend.get_run()` calls remain in the QQ post-ACK composition path
- All 13 qqbot-service tests + 23 qqbot channel tests stay green (ED25519, op=13, webhook port, idempotency preserved)
- The `ingress_runtime.py` and `session_runtime.py` in the qqbot channel package are kept but no longer called from post-ACK

## Reversibility Gate

**One-way-door:** Creating `gateway_client.py` and `event_consumer.py` in `services/qqbot-service/src/qqbot_service/`. These new files are automatically covered by the existing `qqbot-service` gate (#19). Strategy: purely additive — no existing source file is modified until the tracer is proven. The `test_no_wecom_import.py` test must still pass — the new modules must not import from WeCom.

**One-way-door:** Modifying `webhook.py`'s `run_post_ack_composition()` to use the event consumer. Strategy: same fallback pattern as WeCom — when `gateway_client` is None, the old ingress path is used (backward compat). The `QQBotWiredRuntime` dataclass gains an optional `gateway_client` field.

**One-way-door:** QQ-specific delivery concerns — passive reply window, scene-aware delivery, wakeup path. The event consumer must check the passive reply window before delivering (using `check_passive_reply_window()` from the QQ sender) and use the correct scene metadata (c2c vs group) from the normalized inbound. Strategy: the consumer delegates all delivery to `adapter.deliver()`, which already handles these concerns. The consumer only needs to pass the correct `metadata` fields (scene, user_openid, group_openid, msg_id) from the normalized inbound.

Define the following:

1. A dataclass `QQBotEventConsumer` with:
   - `__init__(self, *, gateway_client: GatewayClient, adapter: QQBotChannelAdapter, solution: SolutionBinding | None = None, tenant_id: str = "default-tenant", media_uploader: Callable[[str, bytes], dict[str, Any]] | None = None, progress_interval_seconds: float = 180.0)` — stores all deps. The `media_uploader` for QQ takes `(filename, content_bytes)` and returns a `file_info` dict (QQ's rich media format). When None, file delivery is skipped.

   - `async def consume_and_deliver(self, *, turn: dict[str, Any], scene: str, user_openid: str | None, group_openid: str | None, msg_id: str | None, msg_seq: int | None, conversation_id: str | None = None, session_id: str | None = None, received_at: str | None = None) -> dict[str, Any]` — the main entry point. Steps mirror the WeCom consumer:
     1. Create or reuse Gateway session
     2. Create Gateway run
     3. Consume SSE stream, collecting events
     4. Send intermediate prompts during stream (tool fold "正在检索法规…", plan first "仍在处理", progress interval)
     5. At terminal state, call `aggregate_events()`
     6. Map `BotDelivery` to QQ `ChannelDelivery` calls:
        - `final_message` → `ChannelDelivery(delivery_type="text", content=final_message, metadata={scene, user_openid, group_openid, msg_id, msg_seq})`
        - `cards` → `ChannelDelivery(delivery_type="card", metadata={scene, user_openid, group_openid, msg_id, msg_seq, feedback_target})` — QQ adapter maps this to `build_feedback_keyboard_envelope()`
        - `files` → download artifact, upload via `media_uploader` if available, then `ChannelDelivery(delivery_type="file", metadata={scene, user_openid, group_openid, file_info})`
        - `error_prompt` → `ChannelDelivery(delivery_type="text", content=error_prompt, metadata={scene, ...})`
     7. Return evidence dict

   - `def _map_card_to_delivery(self, card: dict[str, Any], *, scene: str, user_openid: str | None, group_openid: str | None, msg_id: str | None, msg_seq: int | None, run_id: str) -> ChannelDelivery` — maps an elicitation/permission card to a QQ `ChannelDelivery` with `delivery_type="card"`. The QQ adapter's `deliver()` method calls `build_feedback_keyboard_envelope()` for card type. The card content is the first question text (elicitation) or permission description.

   - `def _map_file_to_delivery(self, file_payload: dict[str, Any], *, scene: str, user_openid: str | None, group_openid: str | None, run_id: str) -> ChannelDelivery | None` — maps an artifact to a QQ file delivery. Downloads artifact via `gateway_client.download_artifact()`. If `media_uploader` is available, uploads to get `file_info` dict. If None, returns None (skip in CI).

   - `def _build_delivery_metadata(self, *, scene: str, user_openid: str | None, group_openid: str | None, msg_id: str | None, msg_seq: int | None, received_at: str | None) -> dict[str, Any]` — builds the common metadata dict for QQ deliveries, including scene, user_openid, group_openid, msg_id, msg_seq, received_at, reply_count.

2. Helper functions: `solution_to_dict()`, `is_terminal_event()` — same as WeCom consumer.

Import `aggregate_events`, `BotDelivery` from `platform_contract.bot_degradation`. Import `ChannelDelivery` from `platform_runtime.protocols`. Import `GatewayClient` from `.gateway_client`. Import `QQBotChannelAdapter` from `inkstatute_channels_qqbot.adapter`.

CRITICAL: The consumer must NOT call `runtime.create_run()` or `backend.get_run()`. It delegates all delivery to `adapter.deliver()`, which handles passive reply window checking, scene-specific URLs, and wakeup path. The consumer passes the correct `metadata` fields from the normalized inbound so the adapter can make the right decisions. No imports from `wecom_service`.
