Create `services/wecom-service/tests/test_cross_channel_consistency.py` with test class `TestCrossChannelConsistency` using `unittest.TestCase`. These tests verify that the same Gateway run, when consumed by a bot channel (WeCom) vs a web client, produces semantically equivalent results — the same final message, the same cards, the same files, the same citations.

Tests:

1. `test_same_events_same_final_message` — Given the same fixture events (from `bot_events.json`), call `aggregate_events()` once (simulating the web client's view of the SSE stream) and call `WeComEventConsumer.consume_and_deliver()` once (simulating the bot's view). Assert the `final_message` from `aggregate_events()` matches the content of the text delivery from the WeCom consumer. The semantic result is the same — the bot just delivers it as a non-streaming text message instead of a streaming SSE.

2. `test_same_events_same_cards` — Given events with `elicitation.requested`, assert both `aggregate_events().cards` and the WeCom consumer's card deliveries contain the same card payload (same `interrupt_id`, same questions). The bot maps it to a WeCom template card; the web client renders it as an ask_user card — but the underlying data is the same.

3. `test_same_events_same_files` — Given events with `artifact.created`, assert both `aggregate_events().files` and the WeCom consumer's file deliveries reference the same `artifact_id`. The bot downloads and delivers via WeCom media; the web client provides a download link — but the artifact is the same.

4. `test_same_events_same_citations` — Given events with `citation.recorded`, assert the citations from `aggregate_events()` appear in the WeCom consumer's final message (appended as "引用：" section). The web client shows citations in a reference panel; the bot appends them to the final message — but the citation data is the same.

5. `test_same_events_same_error_prompt` — Given events with `run.state_changed` (failed), assert both `aggregate_events().error_prompt` and the WeCom consumer's error delivery contain "处理失败，请稍后重试或联系管理员".

6. `test_bot_receives_intermediate_prompts_web_does_not` — The bot receives "正在检索法规…" and "仍在处理" as intermediate prompts during the stream. The web client sees the raw events (tool_call, plan) and renders them as progress indicators. Assert the WeCom consumer's deliveries include intermediate prompts, while `aggregate_events().intermediate_prompts` also contains them (the degradation rules produce them for both channels, but the web client renders them differently).

7. `test_output_boundary_double_enforced` — Given events where `message.completed` payload contains backend noise ("gateway: restarting"), assert: (a) the Gateway SSE stream blocks the noise (first enforcement — `GatewaySseStream.encode_event()` returns None), (b) the degradation layer's SILENT/DISCARD rules drop `session.started` and `thought.delta` events (second enforcement), (c) the WeCom consumer's `apply_output_policy()` blocks any remaining noise (third enforcement). Assert no delivery contains the noise text.

8. `test_backend_meta_invisible_in_bot_channel` — Given events with `session.started` (SILENT), `thought.delta` (DISCARD), and `tool_call.*` (FOLD), assert none of these event contents appear in any WeCom delivery. The bot user only sees "正在检索法规…" (folded), not the actual tool call details.

9. `test_gateway_system_noise_invisible` — Given events with text content containing "gateway", "system", "update", "command" keywords (backend noise), assert the output boundary blocks them from all deliveries. This verifies SC#6: "后端 meta / gateway / system 噪声在 bot 通道同样不可见".

10. `test_degradation_rules_from_phase_88` — Verify that the degradation rules used by the consumer are exactly the rules from `packages/platform-contract/bot_degradation.py` (Phase 88). Import `DEGRADATION_RULES` and `aggregate_events` directly and assert the consumer uses them. This verifies SC#1: "降级规则来自 Phase 88 的声明且有测试".

11. `test_full_lifecycle_wecom_tracer` — End-to-end: load `bot_events.json`, create `WeComEventConsumer` with `FakeGatewayClient` and `FakeWeComAdapter`, call `consume_and_deliver()`. Assert: (a) intermediate prompts sent, (b) final message delivered, (c) card delivered, (d) evidence status "completed". This is the WeCom-specific end-to-end tracer.

12. `test_web_equivalence_summary` — Summary test that documents the semantic equivalence: for the same Gateway run, the web client sees streaming events (message.delta → message.completed), while the bot sees a single aggregated final message. The cards, files, citations, and error prompts are identical. The only difference is delivery format (streaming vs non-streaming). Assert this with a documented assertion message.

Create `packages/contract-test-suite/tests/test_bot_output_boundary.py` with test class `TestBotOutputBoundary` using `unittest.TestCase`. These tests verify that the output boundary is enforced at multiple layers for bot channels — the Gateway SSE (first point), the degradation rules (second point), and the channel output policy (third point).

Tests:

1. `test_silent_drops_session_started` — `aggregate_events([{"event_type": "session.started", "seq": 1, "payload": {}}])` returns `BotDelivery(delivered=False)`. The SILENT rule drops it.

2. `test_discard_drops_thought_delta` — `aggregate_events([{"event_type": "thought.delta", "seq": 1, "payload": {"delta": "internal reasoning"}}])` returns `BotDelivery(delivered=False)`. The DISCARD rule drops it. No thought content reaches the bot.

3. `test_fold_collapses_tool_call_to_prompt` — `aggregate_events([{"event_type": "tool_call.started", "seq": 1, "payload": {"tool": "search_law"}}])` returns `BotDelivery(intermediate_prompts=["正在检索法规…"])`. The FOLD rule collapses it to a generic prompt. The actual tool name "search_law" does NOT appear in the output.

4. `test_fold_subsequent_tool_calls_silent` — Multiple `tool_call.*` events produce only ONE "正在检索法规…" prompt. Subsequent tool calls are silent.

5. `test_on_failure_only_delivers_on_failure` — `aggregate_events([{"event_type": "run.state_changed", "seq": 1, "payload": {"status": "succeeded"}}])` returns `BotDelivery(delivered=False)`. Success state changes are silent. But `{"status": "failed"}` produces `error_prompt = "处理失败，请稍后重试或联系管理员"`.

6. `test_gateway_noise_blocked_by_boundary` — Given a `message.completed` event with payload content "gateway: restarting", the `DefaultAssistantOutputBoundary.apply("ordinary_user", "gateway: restarting")` returns `BoundaryAction.BLOCK`. The noise is blocked at the output boundary.

7. `test_system_noise_blocked_by_boundary` — Same test for "system: maintenance" content.

8. `test_degradation_plus_boundary_combined` — Given a mixed event stream with: session.started (SILENT), thought.delta (DISCARD), tool_call.started (FOLD), message.completed with noise (BLOCK), message.completed with clean text (DELIVER). Assert the final `BotDelivery` has: `intermediate_prompts=["正在检索法规…"]`, `final_message` is the clean text (not the noise), `delivered=True`. All noise is invisible.

9. `test_no_backend_meta_in_bot_delivery` — Given events with various backend metadata in payloads (gateway, system, update, command, help, available_commands_update, terminal), assert NONE of these keywords appear in `BotDelivery.final_message`, `intermediate_prompts`, `cards`, `files`, or `error_prompt`. The combined effect of degradation rules + output boundary blocks all backend noise.

10. `test_citation_attach_preserves_clean_text` — Given `message.completed` with clean content + `citation.recorded`, the final message includes the clean content plus a "引用：" section. No noise is introduced by the citation attachment.

11. `test_double_enforcement_documentation` — A documentation test that asserts the output boundary is enforced at: (a) Gateway SSE (`GatewaySseStream.encode_event` returns None for blocked events), (b) degradation rules (SILENT/DISCARD/FOLD/ON_FAILURE filter events), (c) channel output policy (`apply_output_policy()` at delivery time). Import the relevant modules and assert they exist and have the expected interfaces.

12. `test_aggregate_events_pure_function` — Call `aggregate_events()` twice with the same input and assert the results are identical (deterministic). Call with out-of-order events and assert the result is the same as in-order (seq sorting works).
