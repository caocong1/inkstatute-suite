# Plan 94-01: Wave 1 Tracer — apps/desktop scaffold, Tauri shell, Gateway connection, desktop adapters, app shell with TitleBar

## Goal

Create the `apps/desktop` application scaffold with a Tauri 2 shell migrated from `lawyer-desktop`, and prove the end-to-end vertical slice: app launches → connects to Gateway → shows home page → can navigate to workspace. This is the minimal tracer that proves the Tauri app builds, the Gateway connection works with a configurable URL, `@inkstatute/ui-core` components render in a Tauri WebView context, all 6 desktop adapter implementations function (including `WindowAdapter` for native window controls), and the custom `TitleBar` with minimize/maximize/close/drag works.

The tracer establishes the foundational patterns for the entire phase: (1) the Tauri 2 build configuration with `vite-plugin-solid`, port 1420, `decorations: false` for custom TitleBar, `dragDropEnabled: true`, and CSP allowing Gateway connectivity; (2) the desktop adapter implementations — 6 concrete Tauri-backed implementations of ui-core adapter interfaces (FileAdapter via `plugin-dialog`, DropAdapter via `onDragDropEvent` + `classify_dropped_paths`, AppInfoAdapter via `getVersion` + updater plugin, WorkspaceAdapter via `list_directory` Tauri command, DocumentParser via client-side parse, WindowAdapter via `getCurrentWindow()`); (3) the `AuthContext` and `ConversationContext` reused from the web client pattern but adapted for configurable Gateway URL; (4) the app shell with signal-based screen switching (`"home" | "workspace"`, no router) matching the original `lawyer-desktop` architecture; (5) the reduced Tauri command surface — only desktop-specific commands (file reading, directory listing, drag-drop classification, path sandbox) are registered, all agent/session/message commands are removed.

This plan also adds `apps/desktop` to the root `package.json` workspaces array and registers a lightweight `desktop` gate in `scripts/run_v2_gates.py` (typecheck + vitest via a Python wrapper, consistent with the `web` gate pattern from Phase 93).

## Reversibility Gate

**One-way-door: Creating `apps/desktop` and adding it to root workspaces.** Once `apps/desktop` is in the `workspaces` array, bun links `@inkstatute/ui-core` and `@inkstatute/platform-sdk-ts` locally. Removing it later would break the workspace graph. Strategy: the addition is purely additive — no existing workspace entry is modified. Task 94-01-01 verifies the scaffold compiles and the gate is additive before building pages on top.

**One-way-door: Tauri shell configuration.** The `tauri.conf.json` sets `decorations: false` (custom TitleBar, no OS chrome), `dragDropEnabled: true`, and CSP with `connect-src` allowing Gateway URLs. This is a structural decision — once the app is configured for custom chrome, all window management goes through `WindowAdapter`. Strategy: the config is migrated from `lawyer-desktop` with minimal changes (package name, identifier, CSP for Gateway, frontend dist path). The `WindowAdapter` implementation is the only way to control the window.

**One-way-door: Reduced Tauri command surface.** The desktop app registers only ~10 desktop-specific Tauri commands (file reading, directory listing, drag-drop classification, path sandbox, workspace FTS5). All 42 agent/session/message/skill/document invoke() calls are NOT registered — they will be replaced by Gateway HTTP/SSE in Plan 94-03. This is a one-way door because once the commands are removed, there is no local agent fallback. Strategy: the command list is explicitly minimal from the start. The `lib.rs` `generate_handler![]` macro includes only the 10 desktop-specific commands. Agent logic is never present in the desktop app.
