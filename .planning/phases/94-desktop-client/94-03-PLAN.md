# Plan 94-03: Wave 2 — invoke() migration verification, SettingsPanel, AppUpdateBanner, auto-update wiring

## Goal

Verify that all 42 agent/session/message/skill/document `invoke()` calls have been migrated to Gateway HTTP/SSE (success criterion #2), implement the reduced desktop `SettingsPanel` with 4 tabs (workspace, auto-update, file access, about), and port the `AppUpdateBanner` component with download progress and restart prompt. This plan proves that the desktop app's Tauri command surface is minimal (~10-12 desktop-specific commands only), that settings work for desktop-specific configuration, and that the auto-update UI functions with the Tauri updater plugin.

The invoke() migration was structurally achieved in Plan 94-01 (the Tauri shell was created with only desktop-specific commands from the start — no agent commands were ever registered). This plan verifies the migration is complete by asserting that no agent/session/message/skill/document `invoke()` calls exist anywhere in the frontend source, and that all Gateway HTTP/SSE equivalents are properly wired through `PlatformApiClient` and `EventStreamStore`.

## Reversibility Gate

**One-way-door: SettingsPanel tab structure.** The reduced SettingsPanel has 4 tabs (工作区, 自动更新, 文件访问, 关于). The 6 original tabs from lawyer-desktop (provider, skills, sync, MCP, files, about) are reduced because provider/skills/sync/MCP are now platform-side. Once the reduced tab structure is committed, adding back provider/skills tabs would require re-introducing agent logic. Strategy: the 4 tabs are explicitly desktop-specific — workspace FTS5, auto-update, file access sandbox, and about info. No agent configuration UI exists.

**One-way-door: AppUpdateBanner as desktop-only component.** The `AppUpdateBanner` depends on `@tauri-apps/plugin-updater` and `@tauri-apps/plugin-process` — it cannot run in a web context. It is placed in `apps/desktop/src/components/` (not in `@inkstatute/ui-core`) to keep ui-core Tauri-free. Strategy: the component uses `AppInfoAdapter.checkForUpdate()` and `AppInfoAdapter.installUpdate()` from the adapter interface, with the concrete implementation in `desktopAppInfoAdapter`. The adapter abstraction means the component could theoretically work with any update mechanism, but the Tauri plugin imports make it desktop-specific.
