# Plan 08-04 - WeCom Task Flow And Progress Event Runtime

## Objective

Replace the live WeCom bridge's blocking one-shot request model with a contract-compatible asynchronous task flow so long document jobs can acknowledge quickly, emit user-safe progress, complete with text/files, and fail or time out as explicit task states without losing file+text context.

## Background

During live Phase 8 UAT on 2026-06-28, a file+instruction task was received and merged correctly, but the running bridge used Hermes one-shot invocation and the old process killed the job after 240 seconds. Increasing the timeout and adding recurring service notices is only a stopgap. The acceptance path needs a task/event flow:

- WeCom ingress creates a task and returns a short service-owned ACK.
- The agent adapter runs in the background and emits task events.
- The WeCom delivery side sends service-owned progress notices and final text/file artifacts.
- If the user sends another message before the task finishes, the service responds immediately through a control-plane path instead of waiting behind the long task.
- Contract/runtime logs record minimized state transitions and refs, not raw legal payloads.
- Ordinary users never see Hermes meta/gateway/update/command/debug/runtime details.

## Threat Model

<threat_model>
<risk id="T-08-04-timeout" severity="high">Long document tasks can exceed request-style timeouts and appear failed even when Hermes would eventually finish. Mitigation: detach user ACK from task completion and represent running, progress, timeout, completed, and failed states explicitly.</risk>
<risk id="T-08-04-empty-file-turn" severity="high">WeCom can send document and text as adjacent events; processing them separately can produce an empty-message response. Mitigation: retain turn aggregation and make the merged turn the single task input.</risk>
<risk id="T-08-04-progress-leak" severity="high">Intermediate Hermes output may include hidden reasoning, gateway notices, paths, commands, or runtime details. Mitigation: progress messages are generated by InkStatute from task states and pass through output policy; do not forward chain-of-thought.</risk>
<risk id="T-08-04-duplicate-send" severity="medium">Retries, reconnects, or repeated progress loops can duplicate ACKs, progress, files, or final replies. Mitigation: task ids, stage ids, and send idempotency keys dedupe user-visible sends.</risk>
<risk id="T-08-04-backend-lockin" severity="medium">A Hermes-specific progress implementation could block later Codex/provider-model modes. Mitigation: define backend-neutral task event names and keep Hermes-specific one-shot behavior behind the adapter.</risk>
<risk id="T-08-04-conversation-blocking" severity="high">A running long task can monopolize the chat so follow-up user input waits until completion. Mitigation: separate fast conversation control-plane routing from long-running task execution; every new user turn gets an immediate service-owned response and is routed based on active-task state and adapter capabilities.</risk>
<risk id="T-08-04-midtask-update-loss" severity="medium">Follow-up instructions sent during a long task can be ignored or falsely claimed as applied. Mitigation: record each mid-task message as a task event; only claim it was applied when the backend adapter supports live update injection and confirms acceptance.</risk>
</threat_model>

## Artifacts This Phase Produces

- A small WeCom task-flow runtime inside the existing service boundary.
- A backend-neutral active-task router for status/cancel/update/new-task decisions while another task is running.
- Backend-neutral task/progress event dataclasses or structured dictionaries.
- Hermes adapter integration that can run one-shot as a background task while emitting service-owned progress, and can later be replaced by a streaming/event adapter without changing WeCom delivery.
- Tests for turn aggregation, active-task follow-up routing, task state transitions, progress notice dedupe, timeout/failure states, output policy, artifact delivery refs, and privacy.
- Updated Phase 8 UAT/readiness docs marking task-flow evidence as required before the trial clock starts.

## Non-Goals

- Do not expose model chain-of-thought or hidden reasoning to WeCom users.
- Do not rebuild Hermes core, router, session store, skill registry, MCP registry, or model gateway.
- Do not introduce a new external service, database, or queue.
- Do not make the user wait for a running long task before acknowledging or routing their next message.
- Do not tell the user that a mid-task instruction was applied unless the selected backend adapter actually accepted it.
- Do not store raw customer legal text, runtime callback bodies, media files, or generated customer documents in repo artifacts.
