# Plan 01: Wire TenantGuard into Web UIs and admin-console-api views

## Objective

Close the HIGH-severity gap identified in the v1.7 milestone audit: tenant isolation
primitives (Phase 56) exist in `platform-runtime` but are not wired into the Web UI data
access paths (Phase 57). This plan integrates `TenantScopeResolver` and `TenantGuard` into
`admin-console-api` and `lawyer-web-chat`, creates a `TenantScopedContractLogReadModel`
wrapper for tenant-filtered read-model queries, and adds comprehensive tenant isolation
tests across all affected services. When `multi_tenant_enabled=False` (the default), all
behavior is unchanged — zero regression.

## Gap Summary (from v1.7 audit)

| Requirement | Status | Gap |
|-------------|--------|-----|
| TENANT-01 | partial | `TenantGuard.enforce()` never called on admin-console-api read-model queries |
| TENANT-02 | partial | `TenantScopedContractLogStore` exists but not wired into Web UI read path |
| TENANT-03 | partial | `TenantNamespacedCache` verified at primitive level; Web UIs don't use tenant scoping |
| TENANT-04 | partial | Migration test covers primitives only; no assertion of tenant_id in Web UI data paths |

**Root cause:** Phase 56 built the primitives; Phase 57 built the Web UIs with RBAC auth
that extracts `tenant_id` from tokens, but neither phase connected the two — the Web UIs
never call `TenantGuard.enforce()` or apply `ScopedQueryFilter` to data access.

**Safety note:** Since `multi_tenant_enabled` defaults to `False`, this is a latent gap
that only manifests when an operator manually enables the flag. The milestone is safe by
default, but the requirement text ("every read-model query") is not fully satisfied.

## Architecture (Target State)

### Admin Console API data flow (with TenantGuard)

```
Request → handle_admin_get()
  → resolve_identity() → Identity(role, tenant_id)
  → TenantScopeResolver.resolve(TenantScopeRequestContext(identity=identity)) → TenantScope(tenant_id)
  → TenantGuard.enforce(scope) → ScopedQueryFilter(tenant_id, active=True)
  → handle_sessions/tasks/feedback(route_path, route_query, read_model, tenant_filter)
  → TenantScopedContractLogReadModel.list_conversations(tenant_filter) [FILTERED by tenant_id]
```

### Lawyer Web Chat data flow (with TenantGuard)

```
Request → _authenticate() → RbacTokenClaims(tenant_id)
  → TenantScopeResolver.resolve(TenantScopeRequestContext(identity=claims)) → TenantScope(tenant_id)
  → TenantGuard.enforce(scope) → ScopedQueryFilter(tenant_id, active=True)
  → _handle_history/upload/feedback(tenant_id, tenant_filter, handler) [FILTERED by tenant_id]
```

### Disabled mode (multi_tenant_enabled=False)

```
TenantScopeResolver.resolve() → TenantScope.NONE
TenantGuard.enforce(TenantScope.NONE) → ScopedQueryFilter.disabled()
All handlers receive disabled filter → pass through unchanged (v1.6 behavior)
```

## Design Decisions

1. **Wrapper over modification** — `TenantScopedContractLogReadModel` wraps
   `ContractLogReadModel` rather than modifying it. This preserves the existing read model
   API for non-tenant-scoped callers and follows the same pattern as
   `TenantScopedContractLogStore` wrapping `ContractLogStore`.

2. **tenant_id location in records** — When `TenantScopedContractLogStore.append()` injects
   `tenant_id` into event metadata, the `agent_turn` event carries `tenant_id` at the top
   level of the event dict. The read model stores `agent_turn` as a `JsonObject` in
   `ConversationTurnView`. Filtering checks `turn.agent_turn.get("tenant_id")` against the
   filter's `tenant_id`.

3. **admin-web-ui requires NO code changes** — identity already flows through via
   `auth_header` to `admin-console-api`, which re-resolves identity and extracts
   `tenant_id`. Only tests are added to verify end-to-end tenant isolation.

4. **lawyer-web-chat handler signature** — Data handlers (`MessageHistory`,
   `FileUploadHandler`, `FeedbackHandler`) already accept `tenant_id` as a parameter for
   write operations. For read operations, a `ScopedQueryFilter` parameter is added to
   enforce tenant scoping when `multi_tenant_enabled=True`. When the filter is disabled,
   existing behavior is preserved.

5. **Feedback queue filtering** — `handle_feedback` filters `feedback_queue` items by
   `item.get("tenant_id")` when the filter is active. Items without a `tenant_id` field are
   excluded when the filter is active (fail-safe: no tenant_id = no access in multi-tenant
   mode).

6. **Lazy imports** — `TenantScopeResolver`, `TenantGuard`, `TenantScopeRequestContext`,
   and `ScopedQueryFilter` are imported from `platform_runtime` at module level in
   `api.py` and `server.py` (both already import from `platform_runtime.feature_flags`).
   `TenantScopedContractLogReadModel` is imported from `platform_runtime` in
   `views.py` via lazy import to avoid circular dependency risk.
