## Design System

| Property | Value |
|----------|-------|
| Tool | none (stdlib SSR — not React/shadcn) |
| Preset | not applicable |
| Component library | none — Python `html.escape` string templates in `admin-web-ui` |

| Font | `system-ui, sans-serif` (existing admin dashboard) |

Forms POST through admin-web-ui (CSRF) to `admin-console-api` `PUT /config/channels`. Incremental SSR forms are in scope; Phase 78 owns complete CSRF SSR surface verification.

## Spacing Scale

Declared values (multiples of 4), mapped from existing dashboard rem usage (`1rem ≈ 16px`):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Checkbox/label gap, status badge padding |
| sm | 8px | Compact field gaps, table cell padding (`0.4–0.6rem`) |
| md | 16px | Default field stack gap, card padding (`1rem`) |
| lg | 24px | Section padding (`1.5rem`), section bottom margin |
| xl | 32px | Page main padding (`2rem`), header/nav horizontal padding |
| 2xl | 48px | Break between QQ and WeCom channel panels |
| 3xl | 64px | Unused this phase |

Exceptions:
- Dual-knob status row: 8px vertical gap between the two knob rows and the effective summary.
- Touch/click targets for checkboxes and submit: minimum 44×44px hit area (padding around control), even if visual control is smaller.

## Typography

Exactly four sizes, two weights — aligned to existing admin dashboard:

| Role | Size | Weight | Line Height | Usage |
|------|------|--------|-------------|-------|
| Body | 16px (`1rem`) | 400 | 1.5 | Form help text, dual-knob explanations, empty/error body |
| Label | 14px (`0.875rem`) | 600 | 1.4 | Field labels, table keys, nav links (`0.9rem` ≈ 14px) |
| Heading | 18px (`1.125rem`) | 600 | 1.2 | Section titles (`h2` / channel panel titles; existing `1.1rem` → standardize 18px) |
| Display | 20px (`1.25rem`) | 600 | 1.2 | Page brand header only (`InkStatute Admin Dashboard`) |

Do not introduce additional sizes or weights. Monospace for secret-ref values: inherit size from Body/Label; use `ui-monospace, SFMono-Regular, Menlo, Consolas, monospace` for ref inputs and configured-ref display only.

## Layout Contract

One page, two stacked channel panels inside the existing `.main` → `.section` shell:

```
[InkStatute Admin Dashboard header]
[nav … Channel Config …]
[identity bar]
[main]
  [section: Channel Config]
    [flash: success | error]          ← only when present
    [restart notice]                  ← always visible muted help
    [panel.card: QQBot channel]
      dual-knob matrix
      host enabled checkbox
      secret-ref fields
    [panel.card: WeCom channel]
      dual-knob matrix
      host enabled checkbox
      secret-ref fields
    [primary CTA: Save channel config]
[/main]
```

Rules:
- Single composition: one page purpose (channel config). No dashboard widgets, stats, or provider/vision forms (Phases 76–77).
- Cards are interaction containers for each channel form group (existing `.card` pattern) — allowed because they group editable fields.
- Max content width remains `1200px` centered (existing `.main`).
- No SPA client routing; full page reload after POST.

## Dual-Knob Interaction Contract (CHAN-03)

**Hard rule:** UI must show **two independent knobs** plus a derived **effective** line. Never a single “Enable channel” master that writes both or hides one.

| Channel | Knob A (platform, read-only in form) | Knob B (host, editable) | Effective |
|---------|--------------------------------------|-------------------------|-----------|
| QQBot | `RuntimeFeatureFlags.qqbot_channel_enabled` | `channels.qqbot.enabled` | `A AND B` |
| WeCom | `RuntimeFeatureFlags.channel_delivery_enabled` (WeCom platform gate equivalent for MVP) | `channels.wecom.enabled` | `A AND B` |

Display requirements:
1. Each knob shown as its own row: label + boolean state (`ON` / `OFF` with `status-ok` / `status-err` or muted OFF).
2. Platform knob is **read-only** on this form (flag is process/env owned). Show current value from API/UI metadata; do not offer a checkbox that mutates the platform flag from this page.
3. Host knob is an editable checkbox bound to the channel doc `enabled` field (default unchecked / False).
4. Effective line is computed client-side for display **and** must match server-provided effective if API returns it; never editable.
5. Help text under the matrix: “Effective enablement requires both knobs ON”.
6. Tests / acceptance: HTML must contain both platform and host labels; must not contain a single control whose name implies bypassing dual-knob (e.g. no `name="force_enable"` / “Enable live IO”).

## Form Field Contract (CHAN-01, CHAN-02, CHAN-04)

### Shared field UX

| Concern | Contract |
|---------|----------|
| Input type for `*_ref` | `text` (not `password`) — operators edit **references**, not secret material |
| Autocomplete | `autocomplete="off"` on all ref fields |
| Placeholder examples | QQ: `env:INKSTATUTE_QQBOT_APP_SECRET`; WeCom: `env:INKSTATUTE_WECOM_TOKEN` |
| Empty value | Submit as omit/null → store `None`; UI shows “Not set” |
| Configured value | Show the **ref string only** (e.g. `env:FOO`); never a resolved secret |
| Status adjacent to field | “Configured (ref stored)” or “Not set” |
| Validation | Client: optional pattern hint; server: `normalize_config_secret_ref` shapes only. On reject, show Error — validation copy; **do not echo** the rejected raw value if it looks like a planted secret (API already avoids echoing) |
| CSRF | Hidden `csrf_token` field required on POST (stdlib token). Phase 78 verifies full surface; Phase 75 forms that mutate must still include CSRF when present |
| RBAC | ADMIN/OPERATOR only; lawyer/viewer see error or are blocked before form (match API 403) |
| Flag gate | If `operator_config_enabled` is false, render form read-only or disable submit and show Error — flag off |

### QQBot fields (`ChannelsDoc.qqbot`)

| Field | Control | Editable |
|-------|---------|----------|
| Platform `qqbot_channel_enabled` | Read-only status | No |
| `enabled` | Checkbox “Host enabled” | Yes |
| `app_id_ref` | Text ref input | Yes |
| `app_secret_ref` | Text ref input | Yes |
| `token_secret_ref` | Text ref input | Yes |
| `bot_secret_ref` | Text ref input | Yes |
| `channel_id` | Hidden or read-only text `qqbot` | No |
| `metadata` | Not exposed in MVP form | No |

### WeCom fields (`ChannelsDoc.wecom`)

| Field | Control | Editable |
|-------|---------|----------|
| Platform `channel_delivery_enabled` | Read-only status | No |
| `enabled` | Checkbox “Host enabled” | Yes |
| `token_secret_ref` | Text ref input | Yes |
| `encoding_aes_key_secret_ref` | Text ref input | Yes |
| `corp_id_ref` | Text ref input | Yes |
| `channel_id` | Hidden or read-only text `wecom` | No |
| `metadata` | Not exposed in MVP form | No |

### Submit payload shape

POST handler builds section body matching Phase 74 PUT `/config/channels` (object with `qqbot` + `wecom` docs). Prefer unwrapped section value. Do not send raw secret keys (`api_key`, `token`, `password`, `bot_secret`, `encoding_aes_key`, etc.).

|-------|--------|

## Accessibility & Safety

- Every input has a visible `<label for=…>`.
- Dual-knob matrix uses text status, not color alone (`ON`/`OFF` words + color class).
- CSP remains strict (existing server CSP); no inline scripts; no `innerHTML` of untrusted data — all dynamic strings through `html.escape`.
- Output boundary (`AdminUiBoundary`) applies to any free-text API messages before render.
- Never render resolved secrets, `.env` file contents, or store filesystem paths.
- Do not claim live WeCom/QQ acceptance from saving config.
